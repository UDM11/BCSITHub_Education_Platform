Unit 7: Application Layers [4 Hrs.]

7.1 Web, HTTP and HTTPS Protocols

Role of the Application Layer

The Application Layer (Layer 7 in OSI, Layer 4/5 in TCP/IP) is the user interface layer. It provides services directly to application programs, enabling them to communicate across the network. It handles high-level protocols, resource sharing, and remote file access.

HTTP (Hypertext Transfer Protocol)

HTTP is a stateless, request-response protocol used to transfer hypertext documents (HTML, CSS, JS, images) on the World Wide Web.

  • Port Number: Port 80.
  • Stateless Nature: Each request is treated as completely independent. HTTP does not maintain session history. Cookies and Session Tokens are used to maintain state.
  • Connections:
    • Non-persistent (HTTP/1.0): Each request-response pair requires a new TCP connection.
    • Persistent (HTTP/1.1): Multiple requests can be sent over a single TCP connection, reducing overhead.
    • Multiplexing (HTTP/2.0): Allows concurrent requests over a single connection in binary format.

HTTP Message Formats

HTTP messages consist of a Start Line, Headers, and an optional Body: 

  Sample HTTP Request:
    GET /notes/index.html HTTP/1.1
    Host: www.bcsithub.com
    User-Agent: Mozilla/5.0
    Accept-Language: en-US

  Sample HTTP Response:
    HTTP/1.1 200 OK
    Date: Tue, 28 Jul 2026 12:00:00 GMT
    Server: Apache/2.4
    Content-Type: text/html
    Content-Length: 1254

    <!DOCTYPE html><html>... (payload)

HTTPS (HTTP Secure)

HTTPS encrypts HTTP messages using SSL/TLS protocols, ensuring confidentiality, data integrity, and authentication.

  • Port Number: Port 443.
  • How it works: Relies on asymmetric cryptography to exchange symmetric session keys. Digital certificates verified by Certificate Authorities (CAs) prove server authenticity.
  HTTPS / TLS Handshake:

  Client                                             Server
    │                                                  │
    │ ─── ClientHello (Supported Cipher Suites) ─────> │
    │ <── ServerHello + Certificate + Public Key ────── │
    │                                                  │
    │ (Client verifies certificate using CA keys)      │
    │                                                  │
    │ ─── ClientKeyExchange (Pre-master secret encrypted)─> │
    │                                                  │
    │ (Both derive Symmetric Session Keys)              │
    │                                                  │
    │ <── ChangeCipherSpec (Encrypted finish message) ── │
    │ ─── ChangeCipherSpec (Encrypted finish message) ─> │
    │                                                  │
    │ ◄═══ Secure Encrypted HTTP Traffic (Symmetric) ══►│
    ▼                                                  ▼

7.2 DNS (Domain Name System) and Resolution Flow

What is DNS?

The Domain Name System (DNS) is a distributed database that acts as the "phonebook" of the Internet. It translates human-readable domain names (e.g., google.com) into machine-routable IP addresses (e.g., 142.250.190.46). It operates primarily over **UDP Port 53** (uses TCP for zone transfers).

DNS Name Hierarchy

                              Root Level (.)
                                    │
                  ┌─────────────────┴─────────────────┐
                  ▼                                   ▼
          Top-Level Domains (TLD)               Country Codes (ccTLD)
             (.com, .org, .edu)                    (.np, .uk, .in)
                  │                                   │
                  ▼                                   ▼
        Second-Level Domains                Second-Level Domains
             (google, facebook)                  (pokharauniversity, gov)
                  │                                   │
                  ▼                                   ▼
               Subdomains                          Subdomains
             (mail, www)                         (exam, admission)

DNS Query Resolution

  1. Recursive Query: The client queries a local DNS resolver (typically provided by ISP or 8.8.8.8) demanding a complete resolution. The resolver is obligated to find the answer.
  2. Iterative Query: The local resolver queries the root, TLD, and authoritative servers. These servers do not return the IP address directly; instead, they return referrals (pointers) to the next server down the hierarchy.
  DNS Resolution Steps:
  [Client Browser] ──(1. Query google.com)──→ [Local DNS Resolver]

                            ▼                          │
                     [Root Name Server] ───────────────┘
                            │  ▲
                            │  │ 5. Refer to google.com Name Server
       4. Query .com TLD    │                          │
                            ▼                          │
                     [TLD Name Server] ────────────────┘

7.3 Email and File Transfer Protocols

Email Protocols

Email systems involve three main protocols working together to send and retrieve messages:

1. SMTP (Simple Mail Transfer Protocol)

  • Role: Push protocol used to send email from client to server, or transfer email between mail servers.
  • Port Number: TCP Port 25 (unencrypted), Port 587 (TLS), Port 465 (SSL).

2. POP3 (Post Office Protocol version 3)

  • Role: Pull protocol used by clients to retrieve email from the server.
  • Mechanism: "Download and Delete". Emails are downloaded locally to the client device and automatically deleted from the mail server.
    Does not support synchronization across multiple devices.
  • Port Number: TCP Port 110 (unencrypted), Port 995 (SSL/TLS).

3. IMAP (Internet Message Access Protocol)

  • Role: Pull protocol used by clients to retrieve email.
  • Mechanism: "Sync and Store". Emails remain stored on the mail server. Changes made on one client (read, folders, delete) are synchronized across all devices.
  • Port Number: TCP Port 143 (unencrypted), Port 993 (SSL/TLS).

File Transfer Protocols

  • FTP (File Transfer Protocol): Used to transfer files between client and server. Uses two separate connections: TCP Port 21 for Control commands and Port 20 for Data transfer.
    FTP sends usernames and passwords in clear plain text, making it insecure.
  • SFTP (SSH File Transfer Protocol): Safe alternative. Encapsulates control commands and data transfers inside a single, secure **SSH connection (Port 22)**. Files are encrypted during transit.

7.4 DHCP (Dynamic Host Configuration Protocol)

What is DHCP?

DHCP is an application layer protocol used to automatically assign IP addresses, subnet masks, default gateways, and DNS server IPs to devices joining a network. It runs over **UDP Port 67 (Server)** and **UDP Port 68 (Client)**.

The DORA Transaction Flow

DHCP relies on a four-step exchange between the client and the DHCP server: 

  New Client                                           DHCP Server
      │                                                     │
      │ ─── DHCP Discover (Broadcast, "I need an IP!") ────> │
      │ <── DHCP Offer (Unicast/Broadcast, "Try this IP") ── │
      │                                                     │
      │ ─── DHCP Request (Broadcast, "I accept that IP") ──> │
      │ <── DHCP Acknowledge (Unicast, "IP is leased to you")│
      ▼                                                     ▼
  1. Discover: The client broadcasts a packet to locate active DHCP servers on the subnet. Destination IP is 255.255.255.255.
  2. Offer: The DHCP server responds with an available IP address, lease duration, subnet mask, default gateway, and DNS configuration.
  3. Request: The client broadcasts a message accepting the offered IP address. Broadcasting notifies other DHCP servers that their offers were not chosen.
  4. Acknowledge (ACK): The server commits the lease mapping to its database and sends final confirmation to the client.

DHCP Relay Agent

Since DHCP discover and request packets are local layer 2 broadcasts, they cannot pass through routers (which block broadcasts by default). To support clients in multiple subnets without running a separate DHCP server in each subnet, a DHCP Relay Agent is configured on the router interface: 

  [Client] ──(Broadcast Discover)──→ [Relay Agent on Router] ──(Unicast Discover)──→ [DHCP Server (Central)]

The relay agent intercepts the local broadcast discover packet, encapsulates it, and forwards it as a unicast packet directly to the IP address of the remote DHCP server.

7.6 Network Caching Mechanisms

1. DNS Caching

To reduce DNS query traffic and latency, resolved DNS queries are cached at multiple levels:

  • Browser Cache: Web browsers cache DNS records for a short time.
  • OS Cache: Operating systems maintain a local DNS resolver cache. In Windows, this can be viewed with ipconfig /displaydns and cleared using ipconfig /flushdns.
  • Local DNS Server Cache: The ISP or corporate DNS resolver caches results.
  • TTL (Time-to-Live): Each DNS record contains a TTL value (in seconds) set by the domain owner, defining how long resolvers are allowed to cache the record before checking again.

2. Web Caching (Conditional GET)

Web proxies and browsers cache web pages locally. When a client requests a page, the browser checks if the cached copy is stale. To verify without downloading the entire page again, it sends a Conditional GET request to the origin server containing the `If-Modified-Since` header:

  • If the page has not changed, the server responds with 304 Not Modified (empty body). The browser loads the page from cache, saving bandwidth.
  • If the page has changed, the server responds with 200 OK and sends the new page body.

7.7 Application Architecture Paradigms and MIME Types

Application Architectures

Application developers design network applications using specific architectural models:

  • Client-Server Architecture: The most dominant model. Clients send requests to a central, always-on server (e.g., Web, database). Easy to manage but suffers from single point of failure and scaling limits.
  • Peer-to-Peer (P2P) Architecture: Completely decentralized. Nodes (peers) communicate directly with each other. Highly scalable as each new peer adds resources (bandwidth, storage) to the network. Hard to manage and secure (e.g., BitTorrent).
  • Hybrid Architecture: Combines client-server for central coordination and P2P for data transfer (e.g., instant messaging servers tracking online users, but media transfer occurs peer-to-peer).

MIME (Multipurpose Internet Mail Extensions)

Originally, email (SMTP) supported only 7-bit ASCII text messages. MIME is an extension that allows SMTP to transmit:

  • Non-ASCII character sets (unicode, international text).
  • Multiple attachments in a single message.
  • Non-text media payloads (images, audio, video files).
  • Rich text formats (HTML emails).

MIME defines specific headers:
MIME-Version: (typically 1.0)
Content-Type: Defines the type and subtype of data (e.g., text/html, image/png, application/pdf).
Content-Transfer-Encoding: Specifies how binary data is encoded into ASCII (e.g., Base64).

7.8 Peer-to-Peer File Distribution: BitTorrent Mechanics

In P2P architectures, file distribution scales dynamically because peers contribute upstream upload bandwidth:

  • Swarms: The collection of all peers (including seeders and leechers) sharing a specific file.
  • Seeder: A peer that has the complete file and continues to upload pieces to others.
  • Leecher: A peer that is currently downloading pieces of the file while uploading downloaded pieces.
  • Tracker: A central server that tracks all active peers in a swarm, sharing peer list addresses when a new peer joins. Modern torrents use trackerless DHT (Distributed Hash Tables) instead.
  • Choking Algorithm: To prevent free-riding, BitTorrent uses a "tit-for-tat" strategy. Peers upload data only to the top-4 neighbors who are currently uploading to them at the highest rates. Other peers are choked (ignored).
  • Rarest-First Piece Selection: Peers request pieces of the file that are least common in the swarm first, ensuring that rare pieces are replicated quickly and do not disappear if a seeder goes offline.

7.9 State Management: Cookies and Web Sessions

As discussed, HTTP is a stateless protocol. Each transaction is handled independently. To allow personalized user experiences (like maintaining a shopping cart or user login state), websites use cookies:

  • Cookie Creation: When a user visits a server, the server generates a unique session ID and includes it in the HTTP response using the Set-Cookie header:
    Set-Cookie: session_id=abc123xyz; Max-Age=3600; Path=/; Secure; HttpOnly
  • Cookie Storage: The user's browser stores this cookie locally on their device, mapped to the server's domain.
  • Subsequent Requests: For every future request sent to that same domain, the browser automatically includes the cookie in the HTTP request headers:
    Cookie: session_id=abc123xyz
  • State Reconstruction: The server reads the session ID from the cookie header, looks up the matching session data in its database, and reconstructs the user's state.

Cookie Attributes for Security

Attribute Purpose Security Benefit
Secure Directs browser to only send the cookie over encrypted HTTPS connections. Prevents cookie sniffing on public Wi-Fi.
HttpOnly Prevents client-side scripts (JavaScript) from accessing the cookie. Mitigates Cross-Site Scripting (XSS) token theft.
SameSite Controls whether cookies are sent with cross-site requests (Strict, Lax, None). Protects against Cross-Site Request Forgery (CSRF) attacks.
