Phase 2: Progress Report & System Design

2.1 Software Requirements Specification (SRS)

During Phase 2, students translate the conceptual framework from Phase 1 into a detailed technical design. The first step is defining the exact requirements of the software system:

1. Functional Requirements (FR)

Functional requirements define what the software must do—its inputs, behaviors, and outputs. They represent the core features visible to the user:

  • User Authentication: Users must be able to register, log in, reset passwords, and log out securely.
  • Role-Based Access Control (RBAC): Admins see dashboard reports, Doctors edit prescriptions, and Receptionists schedule bookings.
  • CRUD Operations: Authorized staff must be able to Create, Read, Update, and Delete patients, appointments, and bills.
  • Search & Filtering: Users can filter medical logs by Patient ID, Name, or Date Range.
  • Invoice Generation: The system must compile billing transactions and export them as clean, printable PDF invoices.

2. Non-Functional Requirements (NFR)

Non-functional requirements describe how the system performs those functions. They represent operational standards:

NFR Category Standard Target System Specifics
Security Zero plaintext storage. Password hashing using bcrypt; session authorization via JWT tokens.
Performance Response time < 2 seconds. Database queries optimized with indexes; assets minified for fast loading.
Usability Responsive design. Bootstrap or custom CSS grids to support mobile, tablet, and desktop viewports.
Reliability 99.5% Uptime. Local database backups automated daily; graceful exception handling.

2.4 Relational Database Design and Normalization

Designing the database is the most critical backend task in Project II. Students must create an Entity-Relationship Diagram (ERD), map it to tables, and normalize those tables to prevent anomalies.

Database Normalization Worked Example

Normalization systematically splits tables to eliminate redundant data and update anomalies:

Unnormalized Form (UNF) Table

Suppose a student hostel project records room allocations in this format:

StudentID StudentName RoomNo HostelFee WardenName WardenPhone
101 Umesh Darlami A-2 $5,000 Ram Prasad 9851000111
102 Hari Thapa A-2 $5,000 Ram Prasad 9851000111

Anomalies present: Redundancy (WardenName and Phone are repeated for every student in Room A-2). If Ram Prasad's phone changes, we must edit multiple rows (Update Anomaly). If we delete student 102, we might lose Warden phone details if he was the only student in that block (Delete Anomaly).

Converting to First Normal Form (1NF)

Requires that all column values are atomic (no comma-separated lists of phone numbers or items in a single cell). Our initial table satisfies 1NF.

Converting to Second Normal Form (2NF)

Requires satisfying 1NF and ensuring that all non-key attributes are fully functionally dependent on the primary key (no partial dependencies where a column depends on only part of a composite primary key).

Converting to Third Normal Form (3NF)

Requires satisfying 2NF and ensuring that no transitive dependencies exist (no non-key attribute depends on another non-key attribute).

In our hostel table, `WardenName` and `WardenPhone` depend on `RoomNo`, which in turn depends on `StudentID`. This is a transitive dependency:
$$\text{StudentID} \to \text{RoomNo} \to \text{WardenName}$$ To fix this, we split the table into two separate tables:

Table 1: Student_Allocation

StudentID (PK) StudentName RoomNo (FK)
101 Umesh Darlami A-2
102 Hari Thapa A-2

Table 2: Room_Warden_Details

RoomNo (PK) HostelFee WardenName WardenPhone
A-2 $5,000 Ram Prasad 9851000111

The tables are now in **3NF**. Redundancy is minimized, and update/deletion anomalies are eliminated.

2.5 Software Architecture Patterns

Project II requires implementing a structured software pattern rather than unstructured spaghetti coding:

1. Model-View-Controller (MVC) Pattern

  • Model: Manages the business data, schema definitions, and direct database queries (e.g., MySQL schemas or ORM models).
  • View: The user interface presentation layer (HTML pages, CSS sheets, client-side JS views).
  • Controller: The logical brain. Resolves incoming requests, queries the model, and passes the parsed data to the view.

2.7 Boyce-Codd Normal Form (BCNF) Analysis

Boyce-Codd Normal Form (BCNF) is an extension of Third Normal Form (3NF), often referred to as 3.5NF. A table is in BCNF if and only if:
For every non-trivial functional dependency $X \to Y$, **$X$ is a super key** (a primary key or candidate key).

BCNF Violation and Decomposition Case Study

Scenario: A clinic stores doctor specialization details:
- Table: Doctor_Specialty(PatientID, Area, DoctorName)
- Assumptions:
1. A patient can consult multiple doctors, but only one doctor per medical specialty (Area).
2. A doctor can only practice in one specialty (Area).

Functional Dependencies:
1. (PatientID, Area) -> DoctorName (Candidate Key is `(PatientID, Area)`)
2. DoctorName -> Area (Since each doctor has only one specialty)

The Problem: In dependency 2 (DoctorName -> Area), the determinant `DoctorName` is NOT a candidate key/super key because a doctor can treat multiple patients. This violates BCNF!

Solution (Decomposition): We decompose the table into two tables to satisfy BCNF:
1. Doctor_Area(DoctorName {PK}, Area)
2. Patient_Consultation(PatientID {PK}, DoctorName {FK}) Now, in both tables, the determinants are super keys, and no BCNF violation exists.

2.9 UI/UX Design and Wireframing Principles

Designing clean, functional user interfaces is crucial for project adoption and reports:

  • Wireframe Levels:
    - *Low-Fidelity:* Hand-drawn sketches on paper mapping layout blocks and page flows quickly.
    - *Mid-Fidelity:* Digital blocks (using Balsamiq or Figma) showing input placement, buttons, and titles without detailed styling.
    - *High-Fidelity:* Complete UI mockups with exact colors, typography, real text, and clickable transitions.
  • UI Guidelines:
    - *Consistency:* Keep headers, sidebars, buttons, and font sizes matching across all user role dashboards.
    - *Color Strategy:* Use soft neutral backgrounds (white/light gray) with a single distinct primary brand color (e.g., deep blue or teal) and semantic indicators (green for success, orange/red for errors/warnings).
    - *Alerts & Feedback:* Always display toast messages or notifications when users complete operations (e.g., "Patient Saved successfully").

3. Recommended Prototyping Tools

  • Figma (Recommended): A collaborative web-based design tool widely used for vector graphics, UI wireframing, and interactive prototyping.
  • Balsamiq Mockups: Excellent for low-to-mid-fidelity wireframing due to its hand-drawn sketch style that focuses on content structure over color.

UI Design Checklist:
1. *Whitespace:* Ensure adequate breathing room (padding/margin) around text blocks.
2. *Contrast:* Text color must contrast strongly with background color to ensure readability.
