Phase 1: Conceptual Framework and Proposal

1.1 Introduction to BCSIT Project II (PRI 281)

Project II (PRI 281) is a 2-credit practical course in the fourth semester of the Bachelor of Computer System and Information Technology (BCSIT) curriculum. It provides students with hands-on experience in building a medium-scale software system by applying the software engineering principles, database models, and programming skills learned throughout the first four semesters.

Unlike Project I (which is often a basic front-end or console application), Project II requires students to develop a complete, multi-tiered application featuring a dynamic database backend, user role-based access control, data validation, and software architecture patterns (such as MVC).

Evaluation Structure of Project II

Evaluation Stage Percentage Weight Deliverable Expected
Internal Proposal Defense 20% Signed proposal report, conceptual framework slide presentation.
Mid-Term Evaluation 30% Progress report, complete database design, class diagrams, 50% functional coding.
External Viva & Defense 50% Final project report, full software demonstration, testing case logs, external viva defense.

1.2 Structuring the Project Proposal

A project proposal is a formal document that describes the planned system, objectives, methodology, and feasibility. A well-written proposal is crucial because it serves as the roadmap for the entire project. It must follow a structured layout:

  1. Title Page: Contains the project title, course code, student names, roll numbers, submission date, and university logo.
  2. Abstract / Executive Summary: A single paragraph (150-250 words) that briefly summarizes the problem statement, proposed system features, technologies to be used, and expected outcomes.
  3. Introduction and Background: Contextual information about the industry or domain, explaining why the system is relevant.
  4. Statement of the Problem: Clearly defines the limitations, inefficiencies, or challenges of the current manual or existing legacy systems.
  5. Objectives:
    • General Objective: The high-level ultimate goal of the project (e.g., "To design and develop a web-based Clinic Management System").
    • Specific Objectives: Action-oriented, measurable milestones (e.g., "To implement secure Patient Registration," "To generate medical billing invoices," "To store health history records").
  6. Scope and Limitations:
    • Scope: Defines what features the system *will* have (e.g., user profiles, admin dashboards, data reporting).
    • Limitations: Outlines what the system *cannot* do (e.g., "Does not handle real-time payment gateway integration," "Only works inside local area network").
  7. Literature Review: Summarizes existing software solutions, research papers, or platforms, highlighting their strengths and gaps that your project aims to fill. Includes:
    • Theoretical Framework: Software development methodologies (like Agile or Waterfall) and architectures.
    • Empirical Review: Review of similar systems in active market use.
  8. Methodology: Details the Software Development Life Cycle (SDLC) model, data collection techniques, hardware/software specifications, and coding frameworks.
  9. Work Plan (Gantt Chart): Visual timeline showing when each phase (Analysis, Design, Coding, Testing, Documentation) will be performed.
  10. References: Standard bibliographic entries in APA (American Psychological Association) formatting.

1.3 Software Feasibility Analysis

Before coding, students must conduct a **Feasibility Study** to verify whether the project can be realistically developed within the constraints of technology, budget, skills, and timeline:

1. Technical Feasibility

Evaluates whether the development team possesses the technical skills, hardware tools, and software resources needed.
Questions asked: Do we know PHP/Java/Javascript well enough? Are our systems powerful enough to compile the project? Are the required APIs open-source?

2. Economic Feasibility (Cost-Benefit Analysis)

Compares the development and operating costs of the system against its tangible and intangible benefits. Although student projects are academic, a standard commercial CBA must be modeled:
$$\text{ROI} = \frac{\text{Net Financial Benefits} - \text{Development Costs}}{\text{Development Costs}} \times 100\%$$ $$\text{Payback Period} = \frac{\text{Initial Capital Outlay}}{\text{Annual Net Cash Inflow}}$$

3. Operational Feasibility

Determines whether the end-users (e.g., administrative staff, students, customers) will actually use the system and if it fits within daily business procedures. It evaluates user interfaces, required training time, and user acceptance.

4. Schedule Feasibility (Gantt Chart)

Validates if the project can be completed before the final university defense date. A Gantt chart is created to track task progress:

1.4 Modern BCSIT Project II Ideas

To help students choose an appropriate project, here are 10 structured project topics with their core database and business logic:

  1. Online Pharmacy E-Commerce System: Features user ordering, doctor prescription upload, stock warnings for expiring medicines, and admin dashboards.

  9. Employee Attendance and Payroll System: Daily check-in/check-out logs, leave application workflow, tax deduction (Nepal tax bracket calculation), and payslip generation.
  10. IT Asset Tracking and Inventory Management: Tracks computers, monitors, software licenses, and hardware serial keys. Manages check-outs to employees and repairs.

1.5 Sample Project Proposal Template

Below is a full-length project proposal sample for a "Web-Based Clinic Management System". Students can refer to this template to structure their proposals:

A PROPOSAL ON CLINIC MANAGEMENT SYSTEM (MEDCARE)

Prepared By: Umesh Darlami & Team

Course Code: PRI 281 (Project II)

1. Executive Summary

The proposed Clinic Management System, named "MedCare," is a web-based portal designed to automate the medical scheduling, patient record tracking, and billing operations of mid-sized clinics. Currently, many clinics in Nepal rely on paper charts to record patient history and log appointments, leading to scheduling conflicts, data loss, and delays in patient care. MedCare resolves this by building a dynamic system using a MySQL database, an Express/NodeJS backend, and a clean HTML/CSS/JS frontend. The system includes role-based access for Admin, Doctor, and Receptionist, ensuring secure and efficient operations.

2. Problem Statement

Mid-sized medical clinics handle a high volume of outpatient records daily. The manual, paper-based tracking systems present severe limitations:
- Slow Retrieval: Locating a patient's historical paper chart takes several minutes, delaying treatment.
- Data Damage: Paper records are susceptible to physical fire, moisture, and misplacement.
- Inefficient Scheduling: Double-bookings of doctors are common because receptionists lack a real-time calendar synchronization tool.
- Accounting Discrepancies: Manual bill calculation is prone to errors and lacks financial auditing summaries.

3. Project Objectives

General Objective: To design, develop, and test a secure, web-based Clinic Management System (MedCare) to replace paper record-keeping.

Specific Objectives:
1. To design a relational database to store patient profiles, medical histories, appointments, and bills securely.
2. To build an appointment scheduling module with real-time slot checking to prevent double-bookings.
3. To implement role-based dashboards (Receptionist, Doctor, Admin) using JWT sessions.
4. To implement a billing system that automatically calculates costs, taxes, and outputs printable invoices.
5. To perform unit and system testing to achieve a system stability rating of at least 95%.

4. Literature Review

Many clinic software solutions exist, such as open-source Electronic Medical Records (EMR) like OpenEMR. While OpenEMR is highly customizable, it is extremely heavy and has a steep learning curve for local Nepalese clinics. Commercial systems like Practo offer premium SaaS tools, but charge expensive monthly subscriptions that are economically infeasible for small wards or independent general practitioners. MedCare targets this gap by delivering a lightweight, cost-free, and simple-to-operate portal customized with Nepalese tax rates (13% VAT) and localized reporting formats.

5. Proposed Methodology

We will adopt the Agile Scrum Methodology for system development. The project will be divided into 4 main two-week sprints:

  • Sprint 1: System Analysis & Design: Database ERD modeling, schema design, and Figma mockup design.
  • Sprint 2: Core Frontend/Backend Development: Node server setup, database connection, user login, and dashboard templates.
  • Sprint 3: Module Integration: Connecting the Appointment Booking calendar and the Doctor Prescription module with database triggers.
  • Sprint 4: Testing & Final Tuning: Writing Jest unit tests, performing security audits, and compiling the PU report.

Technical Stack:
- Frontend: HTML5, CSS3, JavaScript ES6 (built with responsive design for mobile browsers).
- Backend: Node.js with Express framework.
- Database: MySQL (hosted locally or on AWS RDS).
- Development Tools: VS Code, Git/GitHub, Postman.

6. Hardware & Software Requirements

Hardware:
- CPU: Intel Core i5 or equivalent.
- RAM: 8 GB Minimum.
- Disk Space: 500 MB free space for code and local database storage.

Software:
- Operating System: Windows 10/11 or macOS.
- Database Server: MySQL Server 8.0.
- Web Browser: Google Chrome, Firefox, or Microsoft Edge.
- Runtime Environment: Node.js (v18 or above).

7. Expected Outcomes

Upon successful completion of MedCare:
- Clinics will reduce patient check-in times by 60%.
- Appointments will be double-booking-free due to strict database constraint checking.
- Patients will receive clean, error-free printed invoices.
- Medical histories will be stored securely with access limited to authorized doctors.

  • Elmasri, R., & Navathe, S. B. (2016). Fundamentals of Database Systems (7th ed.). Pearson.

1.6 Proposal Defense Best Practices

When defending your proposal before the internal department committee:

  • Keep Slides Visual: Do not overload slides with text. Use diagrams (like SDLC flowcharts or ASCII Gantt charts) to represent processes.
  • Focus on Scope: Be realistic about what you can build in 12 weeks. If you propose machine learning or payment systems, examiners will expect them fully functional at the final defense.
  • Explain the Database: Prepare to answer how you will structure your database tables and handle relationships (foreign keys).
  • Identify Gaps: Clearly explain how your system is better or more suitable than existing alternative solutions.

1.7 Detailed Financial Feasibility: Cost-Benefit Analysis & NPV

In a professional feasibility study, the economic feasibility must project cash flows and compute Net Present Value (NPV) assuming a 3-year system lifespan.

Worked CBA Matrix

Cost Category Year 0 (Development) Year 1 (Operation) Year 2 (Operation) Year 3 (Operation)
Developer Salaries $60,000 $0 $0 $0
Hosting & Domain $2,000 $1,500 $1,600 $1,700
Training & Support $3,000 $1,000 $1,000 $1,000
Total Costs $65,000 $2,500 $2,600 $2,700
Tangible Savings (Staff reduction/paper) $0 $30,000 $32,000 $35,000
Net Cash Flow -$65,000 +$27,500 +$29,400 +$32,300

Assuming a cost of capital (discount rate) of 10%:
$$NPV = \frac{27,500}{(1.10)^1} + \frac{29,400}{(1.10)^2} + \frac{32,300}{(1.10)^3} - 65,000$$
$$PV(\text{Year 1}) = 27,500 / 1.10 = \$25,000.00$$
$$PV(\text{Year 2}) = 29,400 / 1.21 = \$24,297.52$$
$$PV(\text{Year 3}) = 32,300 / 1.331 = \$24,267.47$$
$$NPV = (25,000 + 24,297.52 + 24,267.47) - 65,000 = 73,564.99 - 65,000 = +\$8,564.99$$
Since $NPV > 0$, the project is economically feasible.

1.8 Software Development Life Cycle (SDLC) Model Selection

Choosing the right development methodology determines how your team manages tasks:

SDLC Model Characteristics When to Use Suitability for Project II
Waterfall Linear, sequential phases. No feedback loops. Complete documentation first. Strictly defined, unchangeable requirements. Low. Hard to adapt if requirements change mid-semester.
V-Model Verification and Validation phases run in parallel. Strict testing. Safety-critical systems (medical hardware, aviation software). Medium. Good testing structure, but too rigid.
Agile Scrum Iterative, divided into 2-4 week Sprints. Regular prototype deliveries. Dynamic projects where requirements evolve. **High (Recommended).** Helps teams debug issues incrementally.

The Agile Scrum Framework

  • Scrum Roles:
    - *Product Owner:* Represents client requirements (the supervisor/examiner).
    - *Scrum Master:* Facilitates meetings and removes bottlenecks (team lead).
    - *Development Team:* Writes code, designs database, runs tests.
  • Scrum Events:
    - *Sprint Planning:* Setting goals for the next 2 weeks.
    - *Daily Standup:* 15-minute sync checking completed work and blocking issues.
    - *Sprint Review:* Demonstrating working software prototype to the Product Owner.
    - *Sprint Retrospective:* Reviewing team performance to improve collaboration.

1.10 Conducting the Literature Review & Identifying Research Gaps

The literature review is not just a summary of what you read; it must demonstrate an analytical synthesis of existing works to find the **Research Gap** (what the existing systems lack that your project provides).

1. Systematic Search Steps

  • Identify Keywords: E.g., "Web-based EMR," "Appointment Scheduling Algorithm," "Clinic Database Security."
  • Academic Databases: Use Google Scholar, ResearchGate, and IEEE Xplore to locate peer-reviewed papers.
  • Document Findings: Extract the methodologies (technologies, architectures) and key findings of each source.

2. Sample Literature Review Synthesis Matrix

Reference & Year System / Methodology Key Strengths Identified Gaps (What is Missing?)
Shrestha & Thapa (2023) PHP-based Hospital Portal. Strong patient booking interface. No role-based permissions; passwords stored in plaintext (security vulnerability).
Sharma et al. (2024) NodeJS/MongoDB Medical Register. Real-time chat, cloud storage. Lacks financial invoice generation and Nepalese tax localizations.
OpenEMR Software (2025) Global open-source EMR platform. Extremely rich clinical customization. Steep learning curve, high setup costs, heavy hardware requirements.

3. Standard APA 7th Edition Citation Formats

In your report, list citations using these precise formats:

  • Journal Article: Author, A. A., & Author, B. B. (Year). Title of the article. Title of the Journal, Volume(Issue), pages.
  • Book: Author, A. A. (Year). Title of the book. Publisher Name.
  • Web Page: Group Name. (Year, Month Day). Title of the page. Site Name. URL

Citation Check:
1. Confirm that all in-text citations (e.g. Sharma et al., 2024) have a matching full entry in the references.
2. Avoid citing unverified blog posts or Wikipedia pages; prioritize peer-reviewed publications and official documentation.
3. Check formatting rules for et al. references (use for three or more authors in-text).
4. Capitalize only the first word of the title in book and article references.
