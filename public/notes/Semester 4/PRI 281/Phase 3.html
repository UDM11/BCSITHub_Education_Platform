3.2 Software Testing & Quality Assurance

Software testing proves the reliability of your system. External examiners often request to see your test logs and test cases during the viva:

1. Testing Levels

  • Unit Testing: Testing individual modules or code blocks in isolation (e.g., verifying if the VAT calculation function returns correct values).
  • Integration Testing: Verifying that different modules interact correctly (e.g., checking if booking an appointment correctly decreases the doctor's free slots count in the database).
  • System Testing: Testing the entire system end-to-end to ensure it meets the SRS specifications.
  • User Acceptance Testing (UAT): Letting a receptionist or administrator test the system to see if it fits daily workflow expectations.

25 Frequently Asked Defense Questions by External Examiners

Be prepared to answer these common questions:

  1. Why did you choose this project topic?
    Answer: Explain the business gap in manual tracking systems and how this solution improves efficiency.
  2. What methodology did you adopt, and why?
    Answer: We used Agile Scrum because it allowed iterative progress, regular feedback, and quick adaptions to requirements.
  3. Explain the primary keys and foreign keys in your database.
    Answer: Be prepared to show your ERD and point out how relationships (like `patient_id` in appointments linking to the patients table) are structured.
  4. How does your system handle double-booking of appointments?
    Answer: Detail the SQL check logic or unique compound indexes placed on doctor schedules.
  5. Is your database normalized? If yes, to what form?
    Answer: Yes, normalized to 3NF. Explain how transitive dependencies were removed by splitting student/warden or patient/doctor details.
  6. What is a foreign key constraint? What does ON DELETE CASCADE do?
    Answer: It ensures referential integrity. `ON DELETE CASCADE` means if a patient is deleted, all their corresponding appointments are automatically deleted.
  7. How did you handle authentication security?
    Answer: We used bcrypt to hash passwords on register, and JWT cookies on login to keep sessions secure.
  8. What is JWT? What does it consist of?
    Answer: JSON Web Token. It consists of Header (algorithm), Payload (user claims/metadata), and Signature (verification key).
  9. What is MVC? Why is it better than procedural programming?
    Answer: Model-View-Controller separation. It makes the codebase modular, reusable, and easy to maintain by separating data queries, UI, and business logic.
  10. How did you test your application? Show your test cases.
    Answer: Point to your test case table in the report. Explain unit testing (Jest) and manual black-box testing.
  11. What are non-functional requirements? Give examples from your project.
    Answer: Page load speed under 2 seconds, secure cookie hashing, responsive mobile layout.
  12. How did you design your user interfaces to be mobile-responsive?
    Answer: Used CSS flexbox/grid layout and CSS media queries (`@media (max-width: 768px)`).
  13. What is sql injection? How does your code prevent it?
    Answer: SQL injection is inserting malicious SQL queries into inputs. We prevent it by using parameterized prepared statements.
  14. Show us the code for your database connection configuration.
    Answer: Be ready to open `config/db.js` or equivalent and explain connection pool creation.
  15. Explain the difference between local storage and cookie sessions.
    Answer: Cookies are sent with every HTTP request automatically and can be set to HttpOnly (preventing XSS), while LocalStorage is accessible by client JavaScript.
  16. What is git? How did your team collaborate using Git?
    Answer: A distributed version control system. We worked on separate feature branches and merged them into a main development branch via Pull Requests.
  17. Where is your application hosted?
    Answer: (If deployed) State Render, Netlify, or Vercel URLs. (If local) Explain local network IP setup.
  18. What is a RESTful API? What HTTP methods did you use?
    Answer: Representational State Transfer API. We used GET (read), POST (create), PUT (update), and DELETE (remove).
  19. What is CORS? How did you handle it?
    Answer: Cross-Origin Resource Sharing. Handled by configuring cors middleware in Express to allow requests from the React frontend port.
  20. How do you prevent cross-site scripting (XSS)?
    Answer: By sanitizing user input data before rendering it in the HTML DOM.
  21. What are the limitations of your project?
    Answer: Point out limitations in your scope (e.g. no real-time video consultation module, lacks SMS prescription alerts).
  22. What would you improve if you had 6 more months?
    Answer: Mention enhancements like payment gateway integration, automatic doctor consultation schedules, or offline support.
  23. How did you estimate project costs? Show your CBA results.
    Answer: Point to your ROI and Payback calculations in Chapter 3.
  24. Explain the difference between GET and POST requests.
    Answer: GET appends parameters to the URL and is used to retrieve data. POST sends data in the request body and is used to modify server state.
  25. What was your role in this project group?
    Answer: Clearly describe your contributions (e.g., database design, backend API routing, frontend interface coding).

3.6 Reference Code Implementation Snippets

Students must be prepared to write or explain core snippets of code during their final defense:

1. Secure Password Hashing & Registration (Node.js/Express)

  const express = require('express');
  const bcrypt = require('bcryptjs');
  const db = require('../config/db');
  const router = express.Router();

  // Registration Route
  router.post('/register', async (req, res) => {
      const { username, email, password } = req.body;
      if (!username || !email || !password) {
          return res.status(400).json({ error: "Missing required fields" });
      }
      try {
          // Hash password using bcrypt (10 salt rounds)
          const salt = await bcrypt.genSalt(10);
          const hashPassword = await bcrypt.hash(password, salt);

          // Parameterized query prevents SQL Injection
          const query = "INSERT INTO users (username, email, password) VALUES (?, ?, ?)";
          db.query(query, [username, email, hashPassword], (err, result) => {
              if (err) {
                  if (err.code === 'ER_DUP_ENTRY') {
                      return res.status(400).json({ error: "Email already registered" });
                  }
                  return res.status(500).json({ error: err.message });
              }
              res.status(201).json({ message: "User registered successfully", id: result.insertId });
          });
      } catch (error) {
          res.status(500).json({ error: "Internal server exception" });
      }
  });

  module.exports = router;

2. Unit Testing a Controller Endpoint using Jest & Supertest

  const request = require('supertest');
  const app = require('../server'); // Express app instance
  const db = require('../config/db');

  describe('POST /api/auth/register', () => {
      // Clear test table entries before running test suite
      beforeAll((done) => {
          db.query("DELETE FROM users WHERE email = 'testuser@gmail.com'", () => {
              done();
          });
      });

      it('should successfully register a new user and return status 201', async () => {
          const res = await request(app)
              .post('/api/auth/register')
              .send({
                  username: 'testuser',
                  email: 'testuser@gmail.com',
                  password: 'password123'
              });
          expect(res.statusCode).toEqual(201);
          expect(res.body).toHaveProperty('message');
          expect(res.body.message).toEqual('User registered successfully');
      });

      it('should fail registration if email is missing and return status 400', async () => {
          const res = await request(app)
              .post('/api/auth/register')
              .send({
                  username: 'testuser',
                  password: 'password123'
              });
          expect(res.statusCode).toEqual(400);
      });
  });

3.7 Continuous Integration and Deployment (CI/CD)

In professional software engineering, code changes are automatically validated and built using **CI/CD Pipelines**. Students should be aware of these automation pipelines:

  • Continuous Integration (CI): Automatically compiles code and runs test suites whenever a developer pushes changes to the GitHub repository. This prevents broken code from being integrated into the master branch.
  • Continuous Deployment (CD): Automatically deploys the validated master branch to public hosting servers (e.g., Render, Netlify) once all tests pass.

Sample GitHub Actions Workflow (.github/workflows/ci.yml)

  name: Node.js CI

  on:
    push:
      branches: [ main, dev ]
    pull_request:
      branches: [ main ]

  jobs:
    build-and-test:
      runs-on: ubuntu-latest
      steps:
      - name: Checkout Code
        uses: actions/checkout@v3

      - name: Setup Node.js
        uses: actions/setup-node@v3
        with:
          node-version: 18
          cache: 'npm'

      - name: Install Dependencies
        run: npm ci

      - name: Run Linting checks
        run: npm run lint --if-present

      - name: Run Test Suite
        run: npm test

3.8 Database Seeding and Migration Scripts

When deploying to production, database structures must be initialized, and test records must be populated. Instead of adding rows manually, developers use **Seed Scripts**:

Sample Node.js Seed Script (seed.js)

  const db = require('./config/db');

  const seedData = async () => {
      console.log('Seeding database tables...');
      
      const insertUser = `
          INSERT INTO users (username, email, password) 
          VALUES ('admin', 'admin@medcare.com', 'hashed_pass_here')
          ON DUPLICATE KEY UPDATE username=username;
      `;
      
      const insertPatients = `
          INSERT INTO patients (name, phone, email, dob, gender) 
          VALUES 
          ('Hari Bahadur', '9851020304', 'hari@gmail.com', '1990-05-12', 'Male'),
          ('Sita Kumari', '9841020304', 'sita@gmail.com', '1995-10-22', 'Female')
          ON DUPLICATE KEY UPDATE name=name;
      `;

      db.query(insertUser, (err) => {
          if (err) throw err;
          console.log('Default admin seeded.');
          
          db.query(insertPatients, (err2) => {
              if (err2) throw err2;
              console.log('Initial test patients seeded successfully.');
              process.exit(0);
          });
      });
  };

  seedData();
