Unit 2: Software Process Models [8 Hrs.]

2.1 A Generic Process Model

A process model provides a specific roadmap for software engineering work. It defines the flow of all activities, actions, and tasks, the degree of iteration, the work products, and the organization of the work that must be done. Each process model defines a distinct flow of activities.

Process Flow

A process flow describes how the framework activities (communication, planning, modeling, construction, deployment) and the actions and tasks that occur within each framework activity are organized with respect to sequence and time. There are four general types of process flow:

  • Linear Process Flow: Executes each of the five framework activities in sequence, beginning with communication and culminating with deployment.
  • Iterative Process Flow: Repeats one or more of the activities before proceeding to the next.
  • Evolutionary Process Flow: Executes the activities in a "circular" manner. Each circuit through the five activities leads to a more complete version of the software.
  • Parallel Process Flow: Executes one or more activities in parallel with other activities (e.g., modeling for one aspect of the software in parallel with construction of another aspect).

2.1.1 Defining a Framework Activity

Each framework activity is populated by a set of software engineering actions. Each action is defined by a task set — a collection of software engineering work tasks, related work products, quality assurance points, and project milestones. For example, the framework activity "Communication" might have an action called "Requirements Elicitation" which contains tasks such as: make a list of stakeholders, invite all stakeholders to meeting, ask questions, record responses, consolidate the list, prioritize requirements, and note areas of uncertainty.

2.1.2 Identifying a Task Set

A task set defines the actual work to be done to accomplish the objectives of a software engineering action. A task set may contain:

  • A list of the tasks to be accomplished
  • The work products to be produced
  • The quality assurance filters to be applied
  • The milestones that mark the completion of sub-activities

Different projects require different task sets. A small, relatively simple project would use a simplified task set. A larger, more complex project would require a more comprehensive task set for each action.

2.1.3 Process Patterns

A process pattern describes a process-related problem that is encountered during software engineering work, identifies the environment in which the problem has been encountered, and suggests one or more proven solutions to the problem.

Process patterns can be defined at different levels of abstraction:

  • Stage patterns: Define a problem associated with a framework activity (e.g., Communication). Example: "CustomerCommunication" pattern addresses establishing a productive channel between developers and customers.
  • Task patterns: Define a problem associated with a software engineering action or work task. Example: "RequirementsGathering" pattern establishes an effective approach to creating a prioritized list of requirements.
  • Phase patterns: Define the sequence of framework activities that occur within the process. Example: "SpiralModel" or "Prototyping" patterns describe the overall process flow.

2.3 Prescriptive Process Models

Prescriptive process models advocate an orderly approach to software engineering. They prescribe a set of process elements — framework activities, software engineering actions, tasks, work products, quality assurance, and change management mechanisms. Each process model also prescribes a process flow — a direction for the overall activities and the interconnections among them.

2.2.1 Waterfall Model (Classic Life Cycle)

The waterfall model is the oldest paradigm for software engineering. It suggests a systematic, sequential approach to software development that begins with customer specification of requirements and progresses through planning, modeling (analysis and design), construction (code and test), and deployment (delivery and maintenance). 

  Communication → Planning → Modeling → Construction → Deployment
       ↓              ↓           ↓            ↓              ↓
  Requirements    Estimating   Analysis     Coding        Delivery
  Gathering       Scheduling   Design       Testing       Support

Phases of the Waterfall Model

  1. Communication (Requirements Gathering): The project requirements are gathered. All requirements should be documented in a requirements document.
  2. Planning (Estimating & Scheduling): Project estimation including resources, cost estimation, and scheduling is done at this stage.
  3. Modeling (Analysis & Design): System and software design is prepared from the requirement specifications. The requirements are translated into a representation that can be assessed for quality before code generation begins.
  4. Construction (Code & Test): The actual coding begins. Once the coding is complete, testing of the code is conducted. Testing uncovers errors in the code.
  5. Deployment (Delivery, Support & Feedback): After successful testing, the product is deployed in the customer's environment. After deployment, the customer provides feedback and maintenance is conducted.

Advantages

  • Simple and easy to understand and use
  • Easy to manage due to the rigidity of the model; each phase has specific deliverables and a review process
  • Phases are processed and completed one at a time
  • Works well for smaller projects where requirements are well understood
  • Clearly defined stages and well-understood milestones

Disadvantages

  • Not suitable for complex or long-duration projects
  • Not suitable when requirements are at a moderate to high risk of changing
  • Working software is produced late in the life cycle
  • No working software is produced until late during the life cycle
  • Integration is done as a "big-bang" at the very end, which can lead to issues
  • High amounts of risk and uncertainty
  • Cannot accommodate changing requirements (inflexible)

Enhanced Waterfall Model (V-Model)

The V-Model is an extension of the waterfall model. Instead of moving down in a linear way, the process steps are bent upward after the coding phase, to form a V shape. Each development stage has a corresponding testing phase. 

  Requirements ─────────────────────── Acceptance Testing
       ↘                                        ↗
  System Design ───────────────── System Testing
       ↘                                ↗
  Architecture Design ──── Integration Testing
       ↘                        ↗
  Module Design ──── Unit Testing
       ↘                ↗
        Implementation

2.2.2 Incremental Process Models

The incremental model combines elements of the linear and parallel process flows. It applies linear sequences in a staggered fashion as calendar time progresses. Each linear sequence produces a deliverable "increment" of the software.

How It Works

  • The first increment is often a core product — basic requirements are addressed, but many supplementary features remain undelivered.
  • The core product is used by the customer (or undergoes detailed review). As a result, a plan is developed for the next increment.
  • The plan addresses the modification of the core product to better meet the needs of the customer and the delivery of additional features and functionality.
  • This process repeats following the delivery of each increment, until the complete product is produced.

Advantages

  • Generates working software quickly and early during the software life cycle
  • More flexible — less costly to change scope and requirements
  • It is easier to test and debug during a smaller iteration
  • Customer can respond to each build and provide feedback
  • Lower initial delivery cost due to reduced functionality per increment

2.2.3 Rapid Application Development (RAD)

RAD is an incremental software development process model that emphasizes an extremely short development cycle (60 to 90 days). RAD is a "high-speed" adaptation of the waterfall model in which rapid development is achieved by using component-based construction.

RAD Phases

  1. Business Modeling: The information flow among business functions is modeled.
  2. Data Modeling: The information flow is refined into a set of data objects needed to support the business.
  3. Process Modeling: Data objects are transformed to achieve the information flow necessary to implement a business function.
  4. Application Generation: RAD assumes the use of fourth generation techniques and reusable components.
  5. Testing and Turnover: Since RAD emphasizes reuse, many components have already been tested. Overall testing time is reduced.

Limitations of RAD

  • Requires sufficient human resources to create the right number of RAD teams
  • Developers and customers must be committed to the rapid-fire activities necessary
  • Not appropriate when technical risks are high (e.g., new technology)
  • Not suitable for systems that cannot be properly modularized

2.2.4 Prototype Model

The prototyping paradigm begins with requirements gathering. The developer and customer meet and define the overall objectives for the software, identify whatever requirements are known, and outline areas where further definition is mandatory. A "quick design" then occurs, focusing on a representation of those aspects of the software that will be visible to the customer/user (e.g., input approaches and output formats).

Types of Prototyping

  • Throwaway Prototyping (Rapid): The prototype is built quickly to explore requirements and then discarded. Development starts fresh with a clean design.
  • Evolutionary Prototyping: The prototype evolves into the final product through progressive refinement. The initial prototype is not discarded.

Advantages

  • Users are actively involved in the development
  • Errors can be detected much earlier
  • Quick user feedback leads to better solutions
  • Missing functionality can be identified easily
  • Confusing or difficult functions can be identified

Disadvantages

  • Risk of insufficient analysis — developers may focus on superficial visible aspects
  • Users may become attached to the prototype and resist changes
  • Developers may try to extend the prototype into the final product, resulting in poor design
  • Can lead to "scope creep" as users keep adding requirements

2.2.5 Spiral Process Model

The spiral model, originally proposed by Barry Boehm, is an evolutionary software process model that couples the iterative nature of prototyping with the controlled and systematic aspects of the waterfall model. It provides the potential for rapid development of increasingly complete versions of the software.

Four Major Activities (Quadrants)

  1. Planning: Determination of objectives, alternatives, and constraints. Includes requirements gathering and project planning.
  2. Risk Analysis: Analysis of alternatives and identification/resolution of risks. Prototypes may be developed to reduce risk.
  3. Engineering: Development of the "next-level product." Includes design, coding, and testing.
  4. Customer Evaluation: Assessment of the results of engineering by the customer. Includes review and feedback for next iteration.
                    Planning          Risk Analysis
                  ┌───────────────┬───────────────┐
                  │  Determine    │  Identify &   │
                  │  objectives,  │  resolve      │
                  │  alternatives,│  risks,       │
                  │  constraints  │  build        │
                  │               │  prototypes   │
                  ├───────────────┼───────────────┤
                  │  Plan next    │  Develop &    │
                  │  phases,      │  verify       │
                  │  Review       │  next-level   │
                  │  results      │  product      │
                  └───────────────┴───────────────┘
               Customer Evaluation    Engineering

Advantages

  • High amount of risk analysis hence avoidance of risk is enhanced
  • Good for large and mission-critical projects
  • Strong approval and documentation control
  • Additional functionality can be added at a later date
  • Software is produced early in the life cycle

Disadvantages

  • Can be a costly model to use
  • Risk analysis requires highly specific expertise
  • Project success is highly dependent on the risk analysis phase
  • Doesn't work well for smaller projects
  • Spiral may go on indefinitely

2.2.6 Rational Unified Process (RUP)

The Rational Unified Process (RUP) is an iterative software development process framework created by Rational Software Corporation (now IBM). RUP is not a single concrete prescriptive process, but rather an adaptable process framework.

RUP Phases

  1. Inception: Establish the business case for the system. Identify all external entities (people and systems) that will interact with the system, and define the nature of the interaction at a high level. Identify all use cases and describe a few significant ones.
  2. Elaboration: Develop an understanding of the problem domain, establish an architectural framework, develop the project plan, identify key risks. At the end of this phase, the "architecture lifecycle" is achieved.
  3. Construction: The system is developed, tested, and integrated. The focus is on developing components and other features of the system. At the end, a beta release of the product is ready.
  4. Transition: The product is transitioned to the user community. Includes final testing (beta test), user training, and system rollout. Feedback from users may generate new requirements for subsequent iterations.

2.2.7 Agile Model: XP and Scrum

Extreme Programming (XP)

Extreme Programming (XP) is an agile process model proposed by Kent Beck. XP uses an object-oriented approach as its preferred development paradigm and encompasses a set of rules and practices that occur within four framework activities: planning, design, coding, and testing.

Key XP Practices:

  • The Planning Game: Customer creates user stories with business value; developers estimate effort
  • Small Releases: Deliver working software frequently (every 1-3 weeks)
  • Metaphor: Simple shared story of how the system works
  • Simple Design: The simplest design that works at any given moment
  • Testing: Unit tests are written first (Test-Driven Development — TDD); acceptance tests defined by customer
  • Refactoring: Restructure code without changing functionality to improve design
  • Pair Programming: All production code is written by two programmers at one computer
  • Collective Ownership: Anyone can change any code anywhere in the system
  • Continuous Integration: New code is integrated into the code base multiple times per day; all unit tests must pass
  • 40-Hour Work Week: No overtime; fresh programmers write better code
  • On-site Customer: A customer representative is available full-time to the team
  • Coding Standards: All code follows a consistent style for communication

Scrum

Scrum is an agile process model developed by Jeff Sutherland and Ken Schwaber. Scrum principles are consistent with the agile manifesto and are used to guide development activities within a process that incorporates the following framework activities: requirements, analysis, design, evolution, and delivery.

Key Scrum Concepts:

  • Product Backlog: A prioritized list of project requirements or features that provide business value for the customer.
  • Sprint: A fixed-length iteration (typically 2-4 weeks) in which a "potentially shippable product increment" is created.
  • Sprint Backlog: A subset of the Product Backlog selected for a specific Sprint. The team commits to completing these items within the Sprint.
  • Daily Scrum (Stand-up): A short daily meeting (15 minutes) where each team member answers three questions: What did I do yesterday? What will I do today? Are there impediments?
  • Sprint Review: At the end of each Sprint, the team demonstrates the working increment to stakeholders and gathers feedback.
  • Sprint Retrospective: The team reflects on the Sprint to identify improvements for the next Sprint.

Scrum Roles:

  • Product Owner: Represents the customer; manages the product backlog
  • Scrum Master: Facilitates the process; removes impediments
  • Development Team: Self-organizing team that delivers the increment

A Toolset for the Agile Process

Agile teams often use tools to manage their work effectively:

  • Project Management: Jira, Trello, Azure DevOps, Asana
  • Version Control: Git (GitHub, GitLab, Bitbucket)
  • CI/CD: Jenkins, GitHub Actions, GitLab CI, Travis CI
  • Communication: Slack, Microsoft Teams, Zoom
  • Documentation: Confluence, Notion, Wiki

2.2.8 Big-Bang Model

The Big-Bang model is a software development model where there is no specific process followed. The development just starts with the required money and efforts as the input, and the output is the software developed — which may or may not be as per customer requirements.

  • Very little planning is required
  • Does not follow any specific process
  • All resources are simply used for software development and coding
  • Useful for very small projects, academic projects, or learning projects
  • Not suitable for large or complex projects
  • High risk; outcome is unpredictable

2.4 Specialized Process Models

2.4.1 Component-Based Development (CBD)

Component-based development incorporates many of the characteristics of the spiral model. It is evolutionary in nature, demanding an iterative approach to the creation of software. However, CBD composes applications from pre-packaged software components (sometimes called COTS — Commercial Off-The-Shelf components).

CBD Activities

  1. Available component-based products are researched and evaluated for the application domain
  2. Component integration issues are considered
  3. A software architecture is designed to accommodate the components
  4. Components are integrated into the architecture
  5. Comprehensive testing is conducted to ensure proper functionality

Advantages

  • Reduces development time significantly
  • Reduces overall development cost
  • Pre-tested components reduce defect density
  • Increases reliability (using proven components)

2.4.2 The Formal Methods Model

The formal methods model encompasses a set of activities that leads to formal mathematical specification of computer software. Formal methods enable software engineers to specify, develop, and verify a computer-based system by applying a rigorous, mathematical notation.

  • Uses formal mathematical specifications (e.g., Z notation, VDM, B Method)
  • Ambiguity, incompleteness, and inconsistency can be discovered more easily through the application of mathematical analysis
  • Provides a mechanism for eliminating many of the problems that are difficult to overcome using other software engineering paradigms
  • Extremely time-consuming and expensive for typical commercial software
  • Primarily used in safety-critical systems (medical devices, avionics, nuclear systems)

2.4.3 Aspect-Oriented Software Development (AOSD)

Aspect-Oriented Software Development provides a process and methodological approach for defining, specifying, designing, and constructing aspects — cross-cutting concerns that pervade the system architecture.

  • Cross-cutting concerns are functionalities that affect multiple modules (e.g., logging, security, transaction management, error handling)
  • In traditional OOP, these concerns get "tangled" with business logic
  • AOSD provides mechanisms to modularize cross-cutting concerns
  • Uses concepts like aspects, pointcuts, joinpoints, and advice
  • Languages/frameworks: AspectJ, Spring AOP, PostSharp

Key Takeaway: No single process model is universally applicable. The choice of process model depends on project characteristics: size, complexity, requirements stability, risk factors, team experience, and customer involvement. Many organizations adopt a hybrid approach, combining elements from multiple models to suit their specific needs.
