Unit 11: Concept of Software Re-engineering [3 Hrs.]

11.1 Steps in Re-engineering

What is Software Re-engineering?

Software re-engineering is the examination and alteration of a system to reconstitute it in a new form. It takes an existing system and re-implements it to improve maintainability, performance, or evolve it to meet new requirements. Re-engineering is different from building new software — it starts with an existing legacy system.

When is Re-engineering Needed?

  • The system is still useful but maintenance costs are escalating
  • The technology stack is obsolete (old languages, platforms, databases)
  • The system has poor documentation and is difficult to understand
  • The architecture cannot accommodate new requirements
  • Performance has degraded over years of patches and modifications
  • Security vulnerabilities cannot be adequately addressed
  • Integration with modern systems is difficult or impossible
  • The cost of maintaining the system exceeds the cost of re-engineering

Steps in the Re-engineering Process

  1. Inventory Analysis:
    • Catalog all existing applications in the organization
    • Assess each application's business value, technical quality, and maintenance history
    • Prioritize applications for re-engineering based on business criticality and condition
    • Create a cost-benefit analysis for re-engineering vs. replacement
  2. Document Restructuring:
    • Review existing documentation; update where outdated or missing
    • Create documentation for undocumented aspects of the system
    • Organize documentation in a standardized format
    • Consider automated documentation generation tools
  3. Reverse Engineering:
    • Analyze the existing source code to understand its structure and behavior
    • Extract design information from the code
    • Create design models (class diagrams, sequence diagrams, DFDs) from the existing code
    • Understand the data structures and database schema
  4. Code Restructuring:
    • Analyze and restructure the existing source code
    • Apply coding standards and best practices
    • Remove dead code, redundant code, and spaghetti code
    • Improve variable naming, function decomposition, and modularity
  5. Data Restructuring:
    • Analyze existing data architecture
    • Normalize database schema if needed
    • Migrate data to new formats or databases
    • Clean and validate data during migration
  6. Forward Engineering:
    • Using the recovered design information, build the new system
    • Implement using modern technologies, languages, and frameworks
    • Apply current best practices in design and architecture
    • Test thoroughly to ensure functional equivalence with the old system
  Re-engineering Process Flow:

  Existing          Inventory    Document     Reverse      Code        Data         Forward      New
  Legacy    ──→     Analysis ──→ Restructuring──→ Engineering──→ Restructuring──→ Restructuring──→ Engineering ──→ System
  System

Approach Description Risk Level Cost

Incremental Replace the system piece by piece over time Moderate Spread over time

11.3 Forward Engineering and Reverse Engineering Process

Forward Engineering

Forward engineering is the traditional process of moving from high-level abstractions and logical, implementation-independent designs to the physical implementation of a system. It follows the natural flow: 

  Requirements → Analysis → Design → Implementation → Testing → Deployment

  Forward Engineering = Taking recovered design and building new system

Reverse Engineering

Reverse engineering is the process of analyzing a system to identify the system's components and their interrelationships, and to create representations of the system in another form or at a higher level of abstraction. It is essentially the opposite of forward engineering: 

  Source Code → Design Recovery → Architecture Recovery → Requirements Recovery

  Reverse Engineering = Analyzing existing system to recover design knowledge

Types of Reverse Engineering

  • Code-Level Reverse Engineering:
    • Analyzing source code to understand logic, algorithms, and data structures
    • Generating flowcharts or pseudocode from source code
    • Identifying design patterns used in the code
  • Data Reverse Engineering:
    • Analyzing database schemas to understand data relationships
    • Creating ER diagrams from existing database structures
    • Understanding data transformations and business rules embedded in data
  • Architecture-Level Reverse Engineering:
    • Understanding the overall system architecture from code and configuration
    • Identifying modules, components, and their interactions
    • Creating component diagrams, deployment diagrams
  • Process Reverse Engineering:
    • Understanding the business processes implemented by the software
    • Recovering business rules from code
    • Creating process flow diagrams

Reverse Engineering Tools

Tool Category Purpose Examples
Static Analysis Tools Analyze source code without executing it SonarQube, PMD, Checkstyle, Understand
Dynamic Analysis Tools Analyze code during execution Profilers, debuggers, trace tools
UML Generation Tools Generate UML diagrams from source code Enterprise Architect, Visual Paradigm, Doxygen
Database Reverse Engineering Generate ER diagrams from database schemas MySQL Workbench, pgModeler, DbVisualizer
Decompilers Convert binary code back to source code JD-GUI (Java), dnSpy (.NET), Ghidra (binary)

11.4 Characteristics of Forward and Reverse Engineering

Characteristic Forward Engineering Reverse Engineering
Direction High-level abstraction → Implementation Implementation → High-level abstraction
Starting Point Requirements/Design documents Existing source code/system
Output Working software system Design documents, models, specifications
Goal Build a new system Understand an existing system
When Used New development, re-engineering (reconstruction phase) Legacy system analysis, re-engineering (understanding phase)
Creativity High (creating new solutions) Analytical (discovering existing solutions)
Documentation Documentation drives development Development artifacts are analyzed to create documentation 
  Forward vs. Reverse Engineering:

  Forward Engineering:
  Requirements ──→ Design ──→ Code ──→ Testing ──→ System
  (Abstract)                                     (Concrete)

  Reverse Engineering:
  System ──→ Code Analysis ──→ Design Recovery ──→ Requirements Recovery
  (Concrete)                                     (Abstract)

  Re-engineering = Reverse Engineering + Forward Engineering

11.5 Restructuring

What is Restructuring?

Restructuring is the transformation of code from one form to another at the same relative level of abstraction, while preserving the subject system's external behavior (functionality and semantics). Restructuring is a subset of re-engineering that focuses on modifying the code's structure without changing its function.

Types of Restructuring

1. Code Restructuring

  • Converting spaghetti code to structured code
  • Replacing GOTO statements with structured control flow
  • Extracting methods/functions from long procedures
  • Renaming variables for clarity
  • Removing dead code and unreachable code
  • Simplifying complex conditional expressions
  • Applying coding standards consistently

2. Data Restructuring

  • Normalizing database tables to reduce redundancy
  • Converting flat files to relational databases
  • Changing data types for better precision or performance
  • Reorganizing data structures for better access patterns
  • Migrating from one database system to another

3. Architecture Restructuring

  • Decomposing monolithic applications into modular components
  • Moving from client-server to web-based architecture
  • Transitioning from monolith to microservices
  • Introducing layers (presentation, business logic, data access)
  • Implementing design patterns to improve structure

Benefits of Restructuring

  • Improved readability and understandability
  • Reduced complexity (lower cyclomatic complexity)
  • Easier maintenance and modification
  • Better testability
  • Reduced technical debt
  • Improved performance (in some cases)

11.6 The Economy of Re-engineering

Cost-Benefit Analysis

Before deciding to re-engineer a system, organizations must evaluate whether the investment is justified. The decision framework considers:

Factor Re-engineer Replace (New Development)
Cost Typically 30-70% of replacement cost Full development cost
Time Generally faster than replacement Longer development timeline
Risk Lower (existing business rules are preserved) Higher (may miss critical business rules)
Business Rules Preserved from existing system Must be rediscovered and reimplemented
Quality Improved but may carry some legacy issues Can be designed for optimal quality
Technology Can modernize incrementally Can use latest technology throughout

When to Re-engineer vs. Replace

  • Re-engineer when:
    • The system has significant business value that cannot be easily replicated
    • The core business logic is sound but the technology is outdated
    • The risk of replacement is too high (mission-critical systems)
    • Budget constraints prevent full replacement
    • The system must remain operational during the transition
  • Replace when:
    • The system architecture is fundamentally flawed
    • The business requirements have changed so drastically that the existing system is irrelevant
    • The technology stack is completely obsolete with no migration path
    • Re-engineering costs would approach or exceed replacement costs
    • A suitable commercial off-the-shelf (COTS) product exists

11.7 Software Reuse

What is Software Reuse?

Software reuse is the process of using existing software artifacts — code, design, specifications, documentation — in the development of new software. Reuse is a fundamental strategy for reducing development cost, improving quality, and accelerating time-to-market.

Levels of Software Reuse

Level What is Reused Example
Code Reuse Functions, classes, modules, libraries Using jQuery library, Apache Commons
Component Reuse Self-contained software components Using a PDF generation component, payment gateway SDK
Design Pattern Reuse Proven design solutions (patterns) Using MVC pattern, Singleton pattern
Architecture Reuse System architecture and frameworks Using Spring Framework, Django, React
Application Reuse Entire applications or application families Using WordPress as a CMS, configuring ERP systems
Knowledge Reuse Domain knowledge, requirements, test cases Reusing requirements templates, test case libraries

Benefits of Software Reuse

  • Reduced development cost: Don't build what already exists
  • Improved quality: Reused components have been tested and proven
  • Faster development: Assemble from existing components rather than building from scratch
  • Reduced risk: Using proven components reduces technical uncertainty
  • Standardization: Promotes consistency across applications

Barriers to Software Reuse

  • Not-Invented-Here (NIH) syndrome: Developers prefer to build from scratch
  • Cost of making components reusable: Creating truly reusable components requires additional design effort (estimated 3-5x more than single-use)
  • Finding reusable components: Lack of catalogs and repositories
  • Trust: Reluctance to use components built by others
  • Maintenance: Who maintains reusable components when bugs are found?
  • Licensing: Legal issues with third-party components
Summary: Software re-engineering is a disciplined approach to modernizing legacy systems through reverse engineering (understanding), restructuring (improving), and forward engineering (rebuilding). It offers a cost-effective alternative to complete replacement while preserving valuable business logic. Software reuse is a key strategy for reducing costs and improving quality, but requires organizational commitment and investment in reusable component infrastructure.
