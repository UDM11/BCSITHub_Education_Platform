9.1 Project Scheduling

What is Project Scheduling?

Project scheduling is the process of converting the project action plan into an operating timetable. It serves as a fundamental tool for project tracking and control. The schedule distributes estimated effort across the planned project duration by allocating the effort to specific software engineering tasks.

Purpose of Project Scheduling

  • Time Management: Determines when each task should start and finish
  • Resource Allocation: Assigns people and resources to tasks at specific times
  • Dependency Tracking: Identifies which tasks depend on the completion of other tasks
  • Progress Monitoring: Provides a baseline against which actual progress can be measured
  • Risk Identification: Helps identify potential bottlenecks and schedule risks
  • Communication: Communicates the plan to all team members and stakeholders
  • Coordination: Ensures all team members understand their roles and deadlines

Basic Scheduling Principles

  1. Compartmentalization: The project must be compartmentalized into a number of manageable activities and tasks. The Work Breakdown Structure (WBS) accomplishes this.
  2. Interdependency: The interdependency of each compartmentalized activity/task must be determined. Some tasks must occur in sequence (serial); others can occur in parallel (concurrent).
  3. Time Allocation: Each task must be assigned some number of work units (e.g., person-days). Each task must be assigned a start date and an end date that are a function of interdependencies and the resource available.
  4. Effort Validation: Every project has a defined number of people on the team. As the schedule is developed, the project manager must ensure that no more than the available number of people are assigned at any given time. This is called resource leveling.
  5. Defined Responsibilities: Every scheduled task should be assigned to a specific team member who is responsible for its completion.
  6. Defined Outcomes: Every scheduled task should have a defined outcome — typically a work product (deliverable) or milestone.
  7. Defined Milestones: Each task or group of tasks should be associated with a milestone — a recognizable point at which a deliverable can be reviewed for quality and adherence to requirements.

Relationship Between People and Effort

The relationship between the number of people working on a project and overall productivity is NOT linear. Doubling the number of people does not halve the development time because:

  • Communication overhead increases as n(n-1)/2 where n is team size
  • Learning time — new team members need time to understand the project
  • Task divisibility — not all tasks can be parallelized
  • Dependency chains — some tasks must be done sequentially
  Effort vs. Duration Tradeoff:

Key Insight: There is an optimal team size for every project. Adding people beyond this optimal point actually increases project duration and cost due to communication overhead and coordination complexity.

9.2 Defining a Task for the Software Project

What is a Task?

A task (also called a work package or activity) is a well-defined unit of project work that has a clear beginning and end, a defined set of deliverables, and can be assigned to one or more team members. Tasks are the building blocks of the project schedule.

Task Characteristics

  • Defined Scope: Clear description of what work is to be done
  • Measurable Output: A deliverable or milestone that can be verified
  • Assignable: Can be assigned to a specific person or team
  • Estimable: Duration and effort can be estimated
  • Bounded: Has a defined start and end date
  • Independent: Has minimal overlap with other tasks

Task Decomposition (From WBS)

Tasks are derived from the WBS through progressive decomposition. The level of decomposition should follow the 8-80 rule: each task should require between 8 hours (1 day) and 80 hours (2 weeks) of effort. Tasks smaller than 8 hours create excessive management overhead; tasks larger than 80 hours are difficult to track and control.

Task Dependencies

Tasks may have four types of dependencies:

Dependency Type Notation Meaning Example
Finish-to-Start (FS) A → B B cannot start until A finishes Coding cannot start until design is complete
Start-to-Start (SS) A ⇒ B B cannot start until A starts Testing plan can start when design starts
Finish-to-Finish (FF) A ⇔ B B cannot finish until A finishes Testing cannot finish until coding finishes
Start-to-Finish (SF) A ← B B cannot finish until A starts Rare; legacy system runs until new system starts

9.3 Project Scheduling and Its Types

Types of Project Schedules

1. Master Schedule

  • High-level schedule showing major milestones and phases
  • Used for executive reporting and stakeholder communication
  • Shows: project start/end, phase boundaries, major deliverables

2. Detailed Schedule

  • Shows all individual tasks, dependencies, resources, and dates
  • Used for day-to-day project management and tracking
  • Typically created and maintained in project management software

3. Milestone Schedule

  • Lists only the key milestones and their target dates
  • Used for high-level tracking and reporting
  • Simpler than the detailed schedule

4. Resource Schedule

  • Shows resource allocation over time
  • Identifies over-allocation and under-utilization
  • Used for resource leveling and optimization

Schedule Representations

Representation Description Best For
Gantt Chart Horizontal bar chart showing tasks against time Visual schedule overview, progress tracking
Network Diagram (PERT/CPM) Graph showing task dependencies and critical path Identifying critical path, analyzing dependencies
Milestone Chart Timeline showing key milestones only Executive reporting, high-level tracking
Resource Histogram Bar chart showing resource usage over time Resource planning and leveling

9.5 PERT and CPM Scheduling

PERT (Program Evaluation and Review Technique)

PERT is a statistical tool used in project management designed to analyze and represent the tasks involved in completing a given project. Developed by the U.S. Navy in the 1950s for the Polaris missile project, PERT uses probabilistic time estimates for each activity.

PERT Time Estimates

PERT uses three time estimates for each activity:

  • Optimistic Time (O): The minimum possible time in the best-case scenario (everything goes right)
  • Most Likely Time (M): The most probable time based on normal conditions
  • Pessimistic Time (P): The maximum possible time in the worst-case scenario (everything goes wrong)

PERT Expected Time Formula

  Expected Time (TE) = (O + 4M + P) / 6

  Standard Deviation (σ) = (P - O) / 6

  Variance (σ²) = [(P - O) / 6]²

PERT Calculation Example

  Activity    O (days)  M (days)  P (days)  TE (days)   σ       σ²

  A           2         4         6         4.0         0.67    0.44
  B           3         5         9         5.3         1.00    1.00
  C           1         3         5         3.0         0.67    0.44
  D           4         6         10        6.3         1.00    1.00
  E           2         3         8         3.7         1.00    1.00
  F           3         4         5         4.0         0.33    0.11
  G           1         2         3         2.0         0.33    0.11

  Example Calculation for Activity B:
  TE = (3 + 4×5 + 9) / 6 = (3 + 20 + 9) / 6 = 32/6 = 5.33 days
  σ  = (9 - 3) / 6 = 6/6 = 1.0 day
  σ² = 1.0² = 1.0 day²

CPM (Critical Path Method)

The Critical Path Method (CPM) identifies the longest path through the project network — the critical path. The duration of the critical path determines the minimum project duration. Any delay in a critical path activity directly delays the project.

CPM Terminology

Term Abbreviation Description
Early Start ES Earliest time an activity can start
Early Finish EF Earliest time an activity can finish (ES + Duration)
Late Start LS Latest time an activity can start without delaying the project
Late Finish LF Latest time an activity can finish without delaying the project
Total Float (Slack) TF LS - ES or LF - EF; amount of time an activity can be delayed
Free Float FF Time an activity can be delayed without affecting successor's ES

CPM Forward and Backward Pass

  Forward Pass (Calculate ES and EF):
    ES of first activity = 0
    EF = ES + Duration
    ES of successor = MAX(EF of all predecessors)

  Backward Pass (Calculate LS and LF):
    LF of last activity = Project Duration
    LS = LF - Duration
    LF of predecessor = MIN(LS of all successors)

  Float (Slack) = LS - ES = LF - EF
  Critical Path: Activities where Float = 0

Complete CPM Worked Example

  Project Network:

  Activity  Duration  Predecessors
  A         3         -
  B         4         -
  C         2         A
  D         5         A
  E         3         B
  F         4         C, E
  G         2         D, F

  Step 1: Draw the Network
                    ┌───┐     ┌───┐

             │      │ 2 │     │ F │

  │ A │──────┤              │ └───┘────→│ G │
  │ 3 │      │      ┌───┐  │           │ 2 │
  └───┘      └─────→│ D │──┼──────────→└───┘
                    │ 5 │  │

  │ B │─────→│ E │──────────┘
  │ 4 │      │ 3 │
  └───┘      └───┘

  Step 2: Forward Pass
  Activity   ES    EF = ES + Duration
  A          0     3
  B          0     4
  C          3     5    (ES = EF of A = 3)
  D          3     8    (ES = EF of A = 3)
  E          4     7    (ES = EF of B = 4)
  F          7     11   (ES = MAX(EF_C=5, EF_E=7) = 7)
  G          11    13   (ES = MAX(EF_D=8, EF_F=11) = 11)

  Project Duration = 13 days

  Step 3: Backward Pass
  Activity   LF         LS = LF - Duration
  G          13         11
  F          11         7     (LF = LS_G = 11)
  D          13         8     (LF = LS_G = 13)  *Wait: LF_D = LS_G = 11
  E          7          4     (LF = LS_F = 7)
  C          7          5     (LF = LS_F = 7)
  A          5          2     (LF = MIN(LS_C=5, LS_D=6) = 5)  
  B          4          0     (LF = LS_E = 4)

  Correction — Let me recalculate properly:
  G: LF = 13, LS = 13 - 2 = 11
  F: LF = LS_G = 11, LS = 11 - 4 = 7
  D: LF = LS_G = 11, LS = 11 - 5 = 6
  E: LF = LS_F = 7, LS = 7 - 3 = 4
  C: LF = LS_F = 7, LS = 7 - 2 = 5
  A: LF = MIN(LS_C, LS_D) = MIN(5, 6) = 5, LS = 5 - 3 = 2
  B: LF = LS_E = 4, LS = 4 - 4 = 0

  Step 4: Calculate Float
  Activity   ES  EF  LS  LF  Float (LS-ES)
  A          0   3   2   5   2
  B          0   4   0   4   0  ←  Critical
  C          3   5   5   7   2
  D          3   8   6   11  3
  E          4   7   4   7   0  ←  Critical
  F          7   11  7   11  0  ←  Critical
  G          11  13  11  13  0  ←  Critical

  Critical Path: B → E → F → G
  Critical Path Duration: 4 + 3 + 4 + 2 = 13 days

PERT vs. CPM Comparison

Aspect PERT CPM
Time Estimates Probabilistic (O, M, P) Deterministic (single estimate)
Focus Time/schedule management Time-cost tradeoff
Best For R&D projects with uncertain durations Construction/routine projects
Origin U.S. Navy (1958) DuPont and Remington Rand (1957)
Activity Duration Uncertain, estimated Known from experience
Crashing Not typically used Supports time-cost crashing analysis

Schedule Compression Techniques

  • Crashing: Adding resources to critical path activities to shorten duration. Increases cost but reduces schedule. Only effective on critical path activities.
  • Fast Tracking: Performing activities in parallel that would normally be done in sequence. Increases risk (of rework) but can significantly reduce schedule.
Summary: Project scheduling transforms the project plan into a time-based roadmap. PERT uses probabilistic estimates for uncertain activities, while CPM uses deterministic durations. The critical path determines the minimum project duration — any delay on the critical path delays the entire project. Effective scheduling requires identifying dependencies, allocating resources, and monitoring progress against the baseline schedule.
