Unit 3: Software Requirement Specification and Modeling [8 Hrs.]

3.1 Software Requirements and Its Types

What is a Software Requirement?

A software requirement is a description of a feature, functionality, or constraint that a software system must satisfy. Requirements serve as the foundation for all subsequent development activities — design, coding, testing, and maintenance. If requirements are wrong, everything built on them will also be wrong.

Types of Software Requirements

1. Functional Requirements

Functional requirements describe what the system should do. They define specific behavior or functions of the system. They specify:

  • What inputs the system should accept
  • What outputs the system should produce
  • What data the system should store
  • What computations the system should perform
  • The timing and synchronization of the above

Examples of Functional Requirements:

  • "The system shall allow users to register with email and password."
  • "The system shall generate monthly sales reports in PDF format."
  • "The system shall send email notifications when an order is placed."
  • "The system shall calculate tax at 13% on all purchases."

2. Non-Functional Requirements (NFRs)

Non-functional requirements describe how the system should perform. They define quality attributes, constraints, and performance criteria. NFRs are often more critical than individual functional requirements because a system that is functionally correct but has poor performance, security, or usability will not satisfy users.

NFR Category Description Example
Performance Speed, throughput, response time "System shall respond within 2 seconds for any query"
Reliability Failure frequency, recoverability "System uptime shall be 99.9%"
Availability System uptime and accessibility "System shall be available 24/7/365"
Security Data protection, authentication "All passwords shall be encrypted using AES-256"
Usability Ease of use, learnability "New users shall complete registration in under 3 minutes"
Scalability Handle growth in users/data "System shall support 10,000 concurrent users"
Maintainability Ease of modification "Code shall follow SOLID principles"
Portability Platform independence "System shall run on Windows, Linux, and macOS"

3. Domain Requirements

Domain requirements are derived from the application domain of the system rather than from the specific needs of the users. They may be new functional requirements, constraints on existing requirements, or specific computations. For example, a medical system may have domain requirements related to patient privacy laws (HIPAA compliance).

4. User Requirements vs. System Requirements

  • User Requirements: Statements in natural language (plus diagrams) of what services the system is expected to provide and the constraints under which it must operate. Written for customers.
  • System Requirements: More detailed descriptions of the software system's functions, services, and operational constraints. Written for developers. The system requirements document should define exactly what is to be implemented.

3.2 Requirement Modeling Approaches

Requirements modeling creates a representation of requirements that helps in understanding, analyzing, and validating them. There are several approaches:

Structured Analysis Approach

  • Uses Data Flow Diagrams (DFDs) to model data flow
  • Uses Entity-Relationship Diagrams (ERDs) for data modeling
  • Uses State Transition Diagrams for behavioral modeling
  • Top-down functional decomposition
  • Process-oriented approach

Object-Oriented Approach

  • Uses UML (Unified Modeling Language) diagrams
  • Use Case Diagrams for functional requirements
  • Class Diagrams for data/structure modeling
  • Sequence and Activity Diagrams for behavioral modeling
  • Centers around objects and their interactions

Agile/User Story Approach

  • Requirements are expressed as user stories
  • Format: "As a [role], I want [feature], so that [benefit]"
  • Acceptance criteria define when a story is "done"
  • Story points estimate effort
  • Product backlog organizes stories by priority

3.3 Requirement Engineering

Definition

Requirement engineering (RE) is a set of activities that help to identify, communicate, and manage the requirements for a software system. It is the process of defining, documenting, and maintaining requirements. RE establishes the groundwork for design and construction.

Requirement Engineering Process

The RE process encompasses seven distinct functions carried out in parallel:

  1. Inception — Understanding the basic problem
  2. Elicitation — Gathering requirements from stakeholders
  3. Elaboration — Refining requirements into analysis model
  4. Negotiation — Resolving conflicts in requirements
  5. Specification — Documenting requirements formally
  6. Validation — Checking requirements for correctness and completeness
  7. Management — Controlling changes to requirements
  Inception → Elicitation → Elaboration → Negotiation
                                              ↓
  Management ← Validation ← Specification ←──┘

Inception

At inception, the software engineer asks a set of context-free questions:

  • Who is behind the request for this work?
  • Who will use the solution?
  • What will be the economic benefit of a successful solution?
  • Is there another source for the solution that you need?

The questions help identify all stakeholders, define measurable benefits, and establish a preliminary basis for communication.

3.4 Eliciting Requirements

What is Requirements Elicitation?

Requirements elicitation is the practice of collecting the requirements of a system from users, customers, and other stakeholders. It seems simple — just ask the customer what they want. But it is far more complex and difficult than it appears.

Problems with Elicitation

  • Scope Problems: The boundary of the system is ill-defined or the customers/users specify unnecessary technical detail that may confuse rather than clarify overall system objectives.
  • Understanding Problems: Customers/users are not completely sure of what is needed, have a poor understanding of the capabilities and limitations of their computing environment, don't have a full understanding of the problem domain, have trouble communicating needs to the system engineer, omit information that is believed to be "obvious," specify requirements that conflict with the needs of other customers/users, or specify requirements that are ambiguous or untestable.
  • Volatility Problems: Requirements change over time.

Elicitation Techniques

1. Interviews

  • Structured Interviews: Pre-defined set of questions
  • Unstructured Interviews: Open-ended discussion
  • Semi-structured: Mix of both approaches
  • Good for understanding stakeholder needs at a high level
  • Can be time-consuming and may miss important details

2. Questionnaires/Surveys

  • Useful when stakeholders are geographically distributed
  • Can reach a large number of stakeholders
  • Must be carefully designed to avoid biased or leading questions

3. Observation (Ethnography)

  • Observing users in their actual work environment
  • Helps discover implicit requirements that users may not articulate
  • Particularly useful for understanding existing workflows

4. Document Analysis

  • Reviewing existing documentation, forms, reports, and procedures
  • Useful for understanding the current system and its limitations

5. Prototyping

  • Building a quick model of the system to help stakeholders visualize requirements
  • Extremely effective for clarifying user interface requirements

6. Brainstorming

  • Group technique for generating creative ideas
  • All ideas are accepted without criticism initially
  • Ideas are then organized, refined, and prioritized

7. Use Case Analysis

  • Describes system behavior from the user's perspective
  • Identifies actors and their interactions with the system
  • Provides scenarios that illustrate system functionality

3.5 Collaborative Requirements Gathering

Collaborative requirements gathering involves multiple stakeholders working together to define requirements. One popular approach is Joint Application Development (JAD):

JAD (Joint Application Development)

  • Structured workshop sessions with key stakeholders
  • Facilitated by a trained moderator (not a participant)
  • Participants include: end users, managers, developers, domain experts
  • Sessions are focused and time-boxed (typically 1-5 days)
  • Results in a comprehensive set of requirements with stakeholder buy-in

Guidelines for Collaborative Gathering

  1. Meetings are conducted at a neutral site and have rules for preparation and participation
  2. An agenda is established that is formal enough to cover all important points but informal enough to encourage the free flow of ideas
  3. A "facilitator" (a customer, developer, or outsider) controls the meeting
  4. A "definition mechanism" (worksheets, flip charts, wall stickers, electronic bulletin boards, chat rooms, or virtual forums) is used
  5. The goal is to identify the problem, propose elements of the solution, negotiate different approaches, and specify a preliminary set of solution requirements

3.6 Requirement Analysis

Once requirements are elicited, they must be analyzed to ensure they are correct, complete, consistent, unambiguous, and feasible. Requirement analysis involves:

Analysis Activities

  • Classification: Grouping requirements into categories (functional, non-functional, domain, interface)
  • Prioritization: Assigning priority levels (Must-have, Should-have, Could-have, Won't-have — MoSCoW method)
  • Conflict Resolution: Identifying and resolving conflicting requirements from different stakeholders
  • Feasibility Analysis: Determining if each requirement is technically and economically feasible within project constraints
  • Modeling: Creating models (DFDs, ERDs, use cases) to represent requirements visually and aid understanding

Quality Attributes of Good Requirements

Attribute Description Example of Violation
Unambiguous Only one interpretation possible "The system should be fast" (what is "fast"?)
Testable Can be verified through testing "The system should be user-friendly" (not testable)
Complete All aspects of the requirement are described Missing error handling scenarios
Consistent No conflicts with other requirements Req-1: "Users can delete accounts" vs Req-2: "User data must be retained forever"
Traceable Can be linked to source and downstream artifacts Requirement without a source or linked test case
Feasible Can be implemented within constraints "System shall respond in 0.001ms" (physically impossible)
Modifiable Can be changed without excessive impact Tightly coupled, redundant requirement statements

3.7 Negotiating Requirements

Requirements from different stakeholders often conflict. Requirements negotiation (also called requirements conflict resolution) is the process of resolving these conflicts. The objective is to develop a "win-win" result — a consensus where all parties feel they have gained something.

Win-Win Negotiation

  • Identify stakeholder "win conditions": What each stakeholder needs from the system to consider it a success
  • Identify conflicts: Where win conditions of different stakeholders are incompatible
  • Negotiate: Find solutions that satisfy all parties, possibly through compromise, creative alternatives, or prioritization
  • Document agreements: Record the negotiated requirements and the rationale behind decisions

Common Negotiation Strategies

  1. Prioritization: Use priority schemes (MoSCoW) to defer less critical requirements
  2. Trade-offs: Reduce scope in one area to accommodate another
  3. Phased Delivery: Deliver high-priority requirements first, defer others to later releases
  4. Cost-Benefit Analysis: Evaluate the cost vs. benefit of conflicting requirements

3.8 Requirement Documentation and Validation

Requirement Documentation

Requirements must be documented in a formal, organized manner. The primary document is the Software Requirements Specification (SRS). Requirements documentation should be:

  • Clear and concise
  • Well-organized and structured
  • Traceable (each requirement has a unique ID)
  • Accessible to all stakeholders
  • Version-controlled

Requirement Validation

Requirement validation checks the requirements document for:

  • Validity: Do the requirements reflect the actual needs of the system?
  • Consistency: Are there any contradictions in the requirements?
  • Completeness: Are all required functions and constraints included?
  • Realism: Can the requirements be implemented with available technology and budget?
  • Verifiability: Can the requirement be checked/tested?

Validation Techniques

  • Requirements Reviews: Systematic manual analysis of requirements by a team
  • Prototyping: Build an executable model to check requirements
  • Test-Case Generation: Write test cases for each requirement; if a test case is difficult to design, the requirement may be difficult to implement or ambiguous
  • Automated Consistency Analysis: Use tools to detect inconsistencies

3.9 Requirement Management

What is Requirements Management?

Requirements management is the process of managing changing requirements during the requirements engineering process and system development. Requirements always change because the business environment changes, stakeholders learn more about what they need, and new priorities emerge.

Key Activities

  • Change Control: Formal process for requesting, evaluating, approving, and implementing changes to requirements
    • Change Request Form
    • Impact Analysis
    • Change Control Board (CCB) review
    • Implementation and verification
  • Requirements Traceability: Maintaining relationships between requirements and other artifacts (design, code, tests)
    • Forward traceability: Requirements → Design → Code → Tests
    • Backward traceability: Tests → Code → Design → Requirements
  • Version Control: Tracking different versions of requirements as they evolve
  • Status Tracking: Monitoring the state of each requirement (proposed, approved, implemented, verified, deleted)

3.10 Scenario, Data, Class and Flow-Oriented Modeling

Scenario-Based Modeling (Use Cases)

Scenario-based modeling views the system from the user's perspective. The primary technique is the use case:

Use Case Elements

  • Actor: An entity (person, system, device) that interacts with the system
  • Use Case: A description of a sequence of actions that provides value to an actor
  • System Boundary: The scope of the system being modeled
  • Relationships:
    • Include: One use case always includes the behavior of another
    • Extend: One use case conditionally extends the behavior of another
    • Generalization: One actor/use case inherits from another

Use Case Template

  Use Case:        Place Order
  Actor:           Customer
  Precondition:    Customer is logged in, cart is not empty
  Main Flow:
    1. Customer clicks "Checkout"
    2. System displays order summary
    3. Customer enters shipping address
    4. Customer selects payment method
    5. Customer confirms order
    6. System processes payment
    7. System generates order confirmation
    8. System sends confirmation email
  Postcondition:   Order is placed, inventory updated
  Alternative Flow:
    6a. Payment fails → System displays error, returns to step 4
    3a. Invalid address → System displays validation error

Data Modeling (Entity-Relationship Diagram)

Data modeling focuses on the data objects (entities) that the system must process and the relationships between them.

  • Entity: A data object (e.g., Customer, Order, Product)
  • Attribute: A property of an entity (e.g., Customer.name, Order.date)
  • Relationship: An association between entities (e.g., Customer PLACES Order)
  • Cardinality: 1:1, 1:N, M:N relationships

Class-Based Modeling

Class diagrams model the static structure of the system by showing:

  • Classes: Templates for objects with attributes and methods
  • Associations: Relationships between classes
  • Aggregation: "Has-a" relationship (weak ownership)
  • Composition: "Part-of" relationship (strong ownership)
  • Inheritance: "Is-a" relationship (generalization/specialization)
  • Multiplicity: Number of instances in the relationship

Flow-Oriented Modeling (DFD)

Data Flow Diagrams (DFDs) show the flow of data through the system:

  • External Entity: Source or destination of data (square)
  • Process: Transforms data (circle/rounded rectangle)
  • Data Store: Repository of data (open rectangle)
  • Data Flow: Movement of data (arrow)

DFD Levels

  1. Context Diagram (Level 0): Shows the entire system as a single process with external entities and data flows
  2. Level 1 DFD: Decomposes the single process into major sub-processes
  3. Level 2 DFD: Further decomposes each Level 1 process
  Context Diagram Example (Online Bookstore):

  ┌──────────┐    Order Details    ┌─────────────┐    Book Info     ┌───────────┐
  │          │ ──────────────────→ │             │ ←───────────── │           │
  │ Customer │                    │  Bookstore  │                │ Publisher │
  │          │ ←────────────────── │   System    │ ──────────────→│           │
  └──────────┘  Order Confirmation └─────────────┘  Purchase Order └───────────┘
                                        ↑ ↓

3.11 Requirement Modeling for Web Apps

Web application requirements modeling has unique considerations due to the nature of web applications (network-intensive, content-driven, continuously evolving).

Special Considerations for WebApps

  • Content Model: Defines the content objects (text, images, video) and their relationships
  • Interaction Model: Describes how users interact with the WebApp (navigation, forms, actions)
  • Functional Model: Defines the processing that occurs (business logic, data manipulation)
  • Navigation Model: Defines the navigation flow through the web pages
  • Configuration Model: Describes the server/client architecture and infrastructure

User Stories for Web Apps (Agile Approach)

  User Story #1:
    As a customer,
    I want to search for books by title, author, or ISBN,
    So that I can quickly find the book I'm looking for.

  Acceptance Criteria:
    - Search results appear within 2 seconds
    - Results are paginated (20 per page)
    - Results can be sorted by relevance, price, or rating
    - Partial matches are supported

  User Story #2:
    As an admin,
    I want to manage book inventory (add, update, delete),
    So that the catalog stays current.

  Acceptance Criteria:
    - Admin can upload book cover images
    - Admin can set price, quantity, and description
    - Changes are reflected immediately on the site

3.12 SRS Documents and Their Importance

What is an SRS Document?

The Software Requirements Specification (SRS) is a comprehensive document that provides a complete description of the behavior of a system to be developed. It includes a set of use cases that describe all the interactions the users will have with the software. The SRS also contains non-functional requirements.

IEEE 830 Standard SRS Template

  1. Introduction
    • 1.1 Purpose
    • 1.2 Scope
    • 1.3 Definitions, Acronyms, and Abbreviations
    • 1.4 References
    • 1.5 Overview
  2. Overall Description
    • 2.1 Product Perspective
    • 2.2 Product Functions
    • 2.3 User Characteristics
    • 2.4 Constraints
    • 2.5 Assumptions and Dependencies
  3. Specific Requirements
    • 3.1 External Interface Requirements (User, Hardware, Software, Communications)
    • 3.2 Functional Requirements
    • 3.3 Performance Requirements
    • 3.4 Design Constraints
    • 3.5 Software System Attributes (Reliability, Availability, Security, Maintainability, Portability)
  4. Appendices
  5. Index

Importance of SRS

  • Agreement: Serves as a contract between the customer and the development team
  • Foundation: Provides the basis for all subsequent design and development
  • Validation: Provides a basis for validating the final product
  • Estimation: Helps in estimating cost, effort, and schedule
  • Communication: Ensures all stakeholders have the same understanding
  • Traceability: Enables forward and backward traceability throughout the SDLC

Characteristics of a Good SRS

Characteristic Meaning
Correct Every requirement stated is one the software shall meet
Unambiguous Every requirement has only one interpretation
Complete All significant requirements have been included
Consistent No requirements conflict with each other
Ranked for Importance Requirements are prioritized
Verifiable Each requirement can be tested
Modifiable Structure allows easy changes
Traceable Each requirement has a clear origin and can be traced forward
Summary: The SRS document is arguably the most important document in the software development lifecycle. A well-written SRS reduces ambiguity, prevents scope creep, provides a basis for testing, and serves as a reference throughout the entire project. Poor or missing requirements are the #1 cause of software project failure.
