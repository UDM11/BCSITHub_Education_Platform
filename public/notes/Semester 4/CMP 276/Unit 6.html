Unit 6: Software Testing and Quality Assurance [4 Hrs.]

6.1 Software Testing Approach

What is Software Testing?

Software testing is the process of executing a program with the intent of finding errors. It is a critical element of software quality assurance and represents the ultimate review of specification, design, and code generation.

According to Glen Myers, testing has the following rules:

  • Testing is a process of executing a program with the intent of finding an error.
  • A good test case is one that has a high probability of finding an as-yet undiscovered error.
  • A successful test is one that uncovers an as-yet undiscovered error.

Testing Objectives

  • Testing is a process of executing the software with the intent of finding and removing errors
  • A good test case is one that has a high probability of uncovering an error
  • Testing cannot show the absence of defects; it can only show their presence
  • Testing should be traceable to customer requirements
  • Testing should be planned long before testing begins
  • Testing should begin "in the small" and progress toward testing "in the large"
  • Exhaustive testing is not possible

Testing Levels

Software testing is typically organized into four levels, each building on the previous: 

  ┌─────────────────────────────────────────────┐
  │         Acceptance Testing                   │  ← Customer validates
  ├─────────────────────────────────────────────┤
  │         System Testing                       │  ← Complete system verified
  ├─────────────────────────────────────────────┤
  │         Integration Testing                  │  ← Modules combined and tested
  ├─────────────────────────────────────────────┤
  │         Unit Testing                         │  ← Individual components tested
  └─────────────────────────────────────────────┘

1. Unit Testing

  • Tests individual components (functions, methods, classes) in isolation
  • Performed by developers during the construction phase
  • Uses stubs and drivers to simulate dependencies
  • Focuses on internal logic, boundary conditions, error handling
  • Tools: JUnit, NUnit, pytest, Mocha

2. Integration Testing

  • Tests the interfaces between components when they are combined
  • Approaches:
    • Top-down integration: Starts with top-level module; uses stubs for lower modules
    • Bottom-up integration: Starts with lowest modules; uses drivers for higher modules
    • Sandwich/Hybrid: Combines both approaches
    • Big-bang: All modules integrated at once (not recommended)

3. System Testing

  • Tests the complete integrated system against requirements
  • Includes functional testing, performance testing, security testing, usability testing
  • Validates that the system meets its specified requirements

4. Acceptance Testing

  • Performed by the customer/end-user
  • Alpha Testing: Conducted at the developer's site by end users
  • Beta Testing: Conducted at the customer's site by end users
  • Validates that the system satisfies the customer's business needs

White-Box Testing (Structural Testing)

White-box testing (also called glass-box testing, structural testing, or clear-box testing) uses the internal structure of the program to design test cases. The tester has access to the source code and tests internal logic.

Basis Path Testing

Basis path testing, proposed by Tom McCabe, enables the tester to derive a logical complexity measure of a procedural design and use this measure as a guide for defining a basis set of execution paths:

  1. Draw the Control Flow Graph (CFG) from the source code
  2. Calculate cyclomatic complexity V(G) = E - N + 2
  3. Determine the basis set of V(G) linearly independent paths
  4. Prepare test cases that force execution of each path in the basis set
  Example:
  void process(int a, int b) {
      int x = 0;                    // Node 1
      if (a > 5) {                  // Node 2 (Predicate)
          x = a;                    // Node 3
      }
      if (b > 10) {                 // Node 4 (Predicate)
          x = x + b;               // Node 5
      }
      printf("%d", x);             // Node 6
  }

  V(G) = 2 (predicates) + 1 = 3

  Basis Paths:
  Path 1: 1 → 2 → 4 → 6          (a ≤ 5, b ≤ 10)
  Path 2: 1 → 2 → 3 → 4 → 6      (a > 5, b ≤ 10)
  Path 3: 1 → 2 → 3 → 4 → 5 → 6  (a > 5, b > 10)

  Test Cases:
  TC1: a=3, b=5   → Expected: x=0
  TC2: a=8, b=5   → Expected: x=8
  TC3: a=8, b=15  → Expected: x=23

Control Structure Testing

  • Condition Testing: Tests each condition in the program
    • Branch Testing: Test each branch (true/false) of every condition
    • Domain Testing: Tests boundary values of conditions
  • Loop Testing: Focuses on the validity of loop constructs
    • Skip loop entirely (zero iterations)
    • Only one pass through the loop
    • Two passes through the loop
    • m passes where m < maximum
    • Maximum minus 1, maximum, maximum plus 1 passes
  • Data Flow Testing: Selects test paths based on the locations of definitions and uses of variables

Black-Box Testing (Functional Testing)

Black-box testing focuses on the functional requirements of the software. The tester treats the software as a "black box" — only knowing inputs and expected outputs.

Black-Box Techniques

1. Equivalence Partitioning

Divides the input domain into classes of data (partitions) from which test cases can be derived. Each partition is expected to be treated the same way by the software. 

  Example: Input field accepts age (1-120)

  Valid Partitions:
    Class 1: 1-120 (valid range)

  Invalid Partitions:
    Class 2: < 1 (below minimum)
    Class 3: > 120 (above maximum)
    Class 4: Non-numeric input

  Test Cases:
    TC1: age = 25   (Class 1 - valid)
    TC2: age = 0    (Class 2 - invalid)
    TC3: age = 150  (Class 3 - invalid)
    TC4: age = "abc"(Class 4 - invalid)

2. Boundary Value Analysis (BVA)

Focuses on testing at the boundaries of input ranges where errors are most likely: 

  Example: Input range 1-120

  Boundary Test Cases:
    TC1: age = 0    (just below minimum)
    TC2: age = 1    (minimum boundary)
    TC3: age = 2    (just above minimum)
    TC4: age = 119  (just below maximum)
    TC5: age = 120  (maximum boundary)
    TC6: age = 121  (just above maximum)

3. Decision Table Testing

Uses a table to represent combinations of conditions and the actions that should result:

Condition Rule 1 Rule 2 Rule 3 Rule 4
Age ≥ 18 T T F F
Has ID T F T F
Action
Allow Entry X
Deny Entry X X X

4. State Transition Testing

Tests the behavior of the system as it transitions between different states:

  • Identify all states the system can be in
  • Identify all events that trigger state transitions
  • Create state transition diagrams
  • Test each valid transition and attempt invalid transitions

System Debugging

Debugging occurs as a consequence of successful testing — when a test case uncovers an error, debugging is the process of finding and removing the cause of that error. Debugging approaches include:

  • Brute Force: Memory dumps, print statements, runtime traces
  • Backtracking: Start from the error symptom and work backward through the code
  • Cause Elimination: Develop a hypothesis for the cause, test the hypothesis, refine until the cause is found (scientific method)
  • Automated Debugging: Using debugger tools (breakpoints, watch variables, step-through execution)

6.3 Software Quality Attributes and Quality Factors

McCall's Quality Factors

McCall's quality model categorizes software quality factors into three perspectives:

1. Product Operation (How well does it run?)

Factor Description
Correctness Extent to which a program satisfies its specifications and fulfills user objectives
Reliability Extent to which a program can be expected to perform its function with required precision
Efficiency Amount of computing resources and code required to perform a function
Integrity Extent to which access to software or data by unauthorized persons can be controlled
Usability Effort required to learn, operate, prepare input, and interpret output

2. Product Revision (How easy is it to change?)

Factor Description
Maintainability Effort required to locate and fix an error in a program
Flexibility Effort required to modify an operational program
Testability Effort required to test a program to ensure it performs its intended function

3. Product Transition (How well does it adapt?)

Factor Description
Portability Effort required to transfer a program from one environment to another
Reusability Extent to which a program can be used in other applications
Interoperability Effort required to couple one system to another

6.4 Software Quality Control and Quality Assurance

Quality Control (QC) vs. Quality Assurance (QA)

Aspect Quality Control (QC) Quality Assurance (QA)
Focus Product-oriented (finding defects) Process-oriented (preventing defects)
When During and after development Throughout the entire lifecycle
Goal Identify and fix defects Improve processes to prevent defects
Activities Testing, reviews, inspections Process definition, audits, training, standards
Responsibility Testing team Everyone in the organization

Statistical Software Quality Assurance (SQA)

  • Collects and categorizes information about software defects
  • Traces each defect to its underlying cause
  • Uses the Pareto principle (80/20 rule): 80% of defects come from 20% of causes
  • Identifies the "vital few" causes and corrects the processes that contribute to them

Software Reliability

Software reliability is defined as the probability of failure-free operation of a computer program in a specified environment for a specified period of time.

  • MTBF (Mean Time Between Failures) = MTTF + MTTR
  • MTTF (Mean Time To Failure)
  • MTTR (Mean Time To Repair)
  • Availability = MTTF / (MTTF + MTTR) × 100%

6.5 Software Safety

Software safety is a software quality assurance activity that focuses on the identification and assessment of potential hazards that may affect software negatively and cause an entire system to fail. Safety-critical software is software that can cause or contribute to a hazardous condition.

  • Examples: Medical device software, avionics, nuclear control systems, automotive systems
  • Requires formal hazard analysis (FMEA, FTA)
  • Often requires certification (DO-178C for avionics, IEC 62304 for medical)
  • Demands rigorous testing, formal verification, and comprehensive documentation

6.6 The ISO 9001 Quality Standards

ISO 9001 is an international standard that specifies requirements for a quality management system (QMS). Organizations use the standard to demonstrate the ability to consistently provide products and services that meet customer and regulatory requirements.

ISO 9001 for Software

  • ISO 9001:2015 is the current version — specifies requirements for a QMS
  • ISO/IEC 90003 provides guidelines for applying ISO 9001 to software
  • Focuses on: documented processes, management responsibility, resource management, product realization, measurement/analysis/improvement
  • Requires regular internal audits and management reviews
  • Certification is obtained through accredited third-party auditors

Key ISO 9001 Principles

  1. Customer focus
  2. Leadership
  3. Engagement of people
  4. Process approach
  5. Improvement (continual)
  6. Evidence-based decision making
  7. Relationship management

6.7 SEI Capability Maturity Model (CMM)

The Capability Maturity Model (CMM), developed by the Software Engineering Institute (SEI) at Carnegie Mellon University, provides a framework for improving software processes. It has been superseded by CMMI (Capability Maturity Model Integration), but the original CMM concepts remain fundamental.

CMM Maturity Levels

Level Name Description Key Characteristics
1 Initial Ad hoc, chaotic No formal processes; success depends on individual effort; heroic programming
2 Repeatable Basic project management Planning, tracking, configuration management; can repeat earlier successes
3 Defined Process standardization Organization-wide standard processes; training; peer reviews
4 Managed Quantitative management Metrics-driven; process and product quality measured; statistical control
5 Optimizing Continuous improvement Proactive process improvement; defect prevention; technology change management 
  CMM Maturity Levels Progression:

  Level 5: Optimizing    ─── Continuous Process Improvement
      ↑
  Level 4: Managed       ─── Quantitatively Managed
      ↑
  Level 3: Defined       ─── Process Standardization
      ↑
  Level 2: Repeatable    ─── Basic Project Management
      ↑
  Level 1: Initial       ─── Ad hoc / Chaotic

6.8 Verification and Validation (V&V)

Definitions

  • Verification: "Are we building the product right?" — Ensures the software correctly implements specific functions. Checks the product against specifications.
  • Validation: "Are we building the right product?" — Ensures the software is traceable to customer requirements. Checks the product against actual user needs.
Aspect Verification Validation
Question Building the product right? Building the right product?
Focus Conformance to specifications Conformance to user needs
Methods Reviews, walkthroughs, inspections Testing, prototyping, user feedback
When Throughout development At the end of development phases
Performed By Development team Testing team, customers
Summary: Software testing and quality assurance are complementary activities that ensure the software meets both its specifications (verification) and user expectations (validation). White-box testing examines internal logic while black-box testing focuses on external behavior. Quality standards (ISO 9001, CMM/CMMI) provide frameworks for consistently producing high-quality software.
