2.1 Software Requirements Specification (SRS)

During Phase 2, teams transition from initial ideas to detailed specifications. The SRS document defines the exact scope:

Functional Requirements (FR)

FRs detail the specific features or processes the system must execute:

  • User Interaction: The system must accept registration input containing email formats and strong passwords.
  • Interactive Gallery: Users must be able to filter image items based on tags and click to expand them in a lightbox.
  • JSON Loading: The interface must fetch external datasets asynchronously and render them into table structures.

Non-Functional Requirements (NFR)

NFRs detail performance, design constraints, and operational quality benchmarks:

NFR Category Standard Benchmark Implementation Strategy
Usability Intuitive and clean layout Maintain consistency via design tokens and CSS variables.
Responsiveness Fluid behavior across all screens Media queries (breakpoints: 768px, 480px) and flexible flex/grid layouts.
Performance Loads under 2 seconds Minimize asset size, optimize script compilation times, and clean up DOM listeners.

2.2 Feasibility Study Guidelines

Every proposal require a comprehensive feasibility check across four essential domains:

  • Technical Feasibility: Evaluating if the available technology stack (HTML5, CSS3, JS, jQuery) matches the application's complexity.
  • Operational Feasibility: Determining whether the user flow is logical and user-friendly.
  • Financial Feasibility: Assessing development costs (typically negligible for student projects using open-source utilities).
  • Schedule Feasibility: Mapping deliverables strictly within the 48-day timeline using a Gantt chart.

2.3 High-Level System Analysis & UI Design

Teams must design user pathways and layout structural diagrams (wireframes or Interface Structure Diagrams) prior to actual implementation.

📊 High-Level Design: A flowchart outlining how data passes from a user input form, gets validated, and populates the dynamic DOM list.

2.4 Client-Side Form Validation (Code Sample)

One of the critical components in the Project I syllabus is form validation. Below is the standard code template for client-side form validation using JavaScript:

// Client-Side Validation Script
document.getElementById('registrationForm').addEventListener('submit', function(event) {
    let username = document.getElementById('username').value;
    let email = document.getElementById('email').value;
    let emailPattern = /^[^\s@]+@[^\s@]+\.[^\s@]+$/;

    if (username.trim() === '') {
        alert('Username cannot be empty.');
        event.preventDefault();
    } else if (!emailPattern.test(email)) {
        alert('Please enter a valid email address.');
        event.preventDefault();
    }
});

2.5 Mid-Term & End-Term Defenses

To pass the intermediate evaluations successfully, teams must show consistent progress:

  • Mid-Term (15% Weight): Teams must present two printed copies of the formal proposal report, along with slides and a working prototype demonstrating early features (e.g., raw HTML/CSS shell).
  • End-Term (25% Weight): The project must have at least 60% of the core functionality completed (working forms, validation, sliders, and structural layout styling fully integrated).
