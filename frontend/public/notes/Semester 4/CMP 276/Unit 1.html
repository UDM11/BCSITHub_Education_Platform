Unit 1: Software and Software Engineering [4 Hrs.]

1.1 The Nature of Software

What is Software?

Software is a collection of instructions (computer programs) that, when executed, provide desired features, function, and performance. It also includes data structures that enable the programs to adequately manipulate information, and descriptive information (documents) in both hard copy and virtual forms that describe the operation and use of the programs.

Characteristics of Software

  • Software is developed or engineered; it is not manufactured in the classical sense. Unlike hardware, software does not have physical components that are assembled. It is created through a process of analysis, design, coding, and testing. Although similarities exist between software development and hardware manufacturing, the two activities are fundamentally different.
  • Software doesn't "wear out." Hardware components are subject to environmental effects such as dust, vibration, abuse, temperature, and humidity that cause them to wear out over time. Software is not susceptible to these environmental maladies. However, software does deteriorate — when changes are made, errors can be introduced, and as changes accumulate, the software degrades.
  • Although the industry is moving toward component-based construction, most software continues to be custom built. Reusable software components have been developed, but wide-scale reuse is still limited. A software component should be designed and implemented so that it can be reused in many different programs.

The Software "Bathtub Curve" vs. Hardware Failure Rate

Hardware exhibits a failure rate curve called the "bathtub curve." Early failures (infant mortality) decline, followed by a steady-state period of low failure, and finally a rise in failure rate as components age (wear-out). Software, in contrast, does not exhibit wear-out failures. Instead:

  • Initially, defect rate is high (undiscovered bugs), then declines as defects are corrected.
  • However, each change (patch/update) introduces side effects (new defects), causing occasional spikes in defect rate.
  • Over time, the defect rate increases due to accumulated changes, making the software progressively harder to maintain.
Key Insight: Software does not wear out, but it deteriorates due to the cumulative effect of change. This is why software maintenance is one of the most expensive phases of the software lifecycle.

Dual Role of Software

Software is both a product and a vehicle for delivering a product. As a product, it delivers computing potential. As a vehicle, it acts as the basis for the operation of a computer (operating system), the communication of information (networks), and the creation and control of other programs (software tools and environments).

1.2 Software Application Domains

Software can be applied in any situation for which a pre-specified set of procedural steps has been defined. The following application domains describe the breadth of software applications:

1. System Software

A collection of programs written to service other programs. System software processes complex but determinate information structures. Examples include: compilers, editors, file management utilities, operating system components, networking software, and telecommunications processors.

2. Application Software

Stand-alone programs that solve a specific business need. Applications in this area process business or technical data in a way that facilitates business operations or management/technical decision making. Examples: point-of-sale transaction processing, real-time manufacturing process control.

3. Engineering/Scientific Software

Software that has been characterized by "number crunching" algorithms. Applications range from astronomy to volcanology, from automotive stress analysis to orbital dynamics of the space shuttle, and from molecular biology to automated manufacturing. Modern engineering/scientific software uses computer-aided design, system simulation, and other interactive applications.

4. Embedded Software

Software that resides within a product or system and is used to implement and control features and functions for the end user and for the system itself. Examples: digital functions in an automobile (fuel control, dashboard displays, braking systems), microwave oven controls, and industrial robots.

5. Product-Line Software

Software designed to provide a specific capability for use by many different customers. It can focus on a limited and esoteric marketplace (e.g., inventory control products) or address mass consumer markets (e.g., word processing, spreadsheets, computer graphics, multimedia, entertainment, database management, personal and business financial applications).

6. Web/Mobile Applications

This broad category encompasses a wide array of applications spanning the network. Web applications encompass everything from simple informational pages to sophisticated e-commerce applications, social media platforms, and cloud-based SaaS products. Mobile applications extend the reach to smartphones and tablets with native and hybrid development approaches.

7. Artificial Intelligence Software

Software that makes use of non-numerical algorithms to solve complex problems that are not amenable to computation or straightforward analysis. Applications include robotics, expert systems, pattern recognition (image and voice), artificial neural networks, theorem proving, game playing, natural language processing, and machine learning systems.

1.3 Legacy Software

Definition

Legacy software refers to older programs that were developed decades ago and have been continually modified to meet changes in business requirements and computing platforms. These systems are often critical to business operations but may use outdated technologies, designs, or coding standards.

Characteristics of Legacy Software

  • Longevity: These systems were developed many years ago (sometimes 20-30+ years ago) and continue to serve critical business needs.
  • Poor Quality: Over decades of modification, the original design may have degraded. The code may be poorly documented, difficult to understand, and hard to test.
  • Inextensible Design: The architecture may not readily accommodate extension to interoperate in a network environment, or to integrate with modern databases.
  • Spaghetti Code: Decades of patches, fixes, and modifications may have resulted in convoluted code with complex interdependencies.
  • Business Critical: Despite all their problems, legacy systems often contain business rules and processes that are vital to the organization.

Why Legacy Software Must Be Updated

Legacy software must evolve for one or more of these reasons:

  • The software must be adapted to meet the needs of new computing environments or technology.
  • The software must be enhanced to implement new business requirements.
  • The software must be extended to make it interoperable with other more modern systems or databases.
  • The software must be re-architected to make it viable within an evolving computing environment.
Legacy Dilemma: The cost of replacing legacy software is often enormous, but the cost of maintaining it continues to grow. Organizations face the difficult decision of whether to invest in modernization (re-engineering) or continue with costly maintenance.

1.4 The Unique Nature of WebApps

What Are WebApps?

Web applications (WebApps) are a category of software that is network-intensive, content-driven, and continuously evolving. They are accessed through web browsers and delivered over the internet or an intranet. WebApps have several unique attributes that distinguish them from conventional software:

Attributes of WebApps

  • Network Intensiveness: WebApps reside on a network and must serve the needs of a diverse community of clients. They operate across the internet, intranet, or extranet.
  • Concurrency: A large number of users may access the WebApp at the same time. Usage patterns are unpredictable, and the system must handle variable loads.
  • Unpredictable Load: The number of users can vary by orders of magnitude from day to day. The system must handle peak loads without degradation.
  • Performance: If a WebApp user must wait too long (beyond a few seconds), the user may go elsewhere. Performance is critical for user retention.
  • Availability: Users expect 24/7/365 availability. Downtime is unacceptable for many web-based applications, especially e-commerce and financial services.
  • Data Driven: The primary function of many WebApps is to use hypermedia to present text, graphics, audio, and video content to the end user. Content management is a critical concern.
  • Content Sensitive: The quality and aesthetic nature of content remains an important determinant of the quality of a WebApp.
  • Continuous Evolution: Unlike conventional applications where updates are released at defined intervals, WebApps evolve continuously. Content and functionality are updated frequently, sometimes multiple times per day.
  • Immediacy: The time-to-market for WebApps is often a matter of days or weeks, requiring agile and rapid development methodologies.
  • Security: Because WebApps are available via network access, it is difficult to limit the population of end users. Protecting sensitive content and providing secure data transmission is essential.
  • Aesthetics: The "look and feel" of a WebApp is arguably more important than for other software categories. Attractive UI/UX design directly impacts user engagement and satisfaction.
WebApp Attribute Impact on Development
Network Intensive Must design for distributed architecture and network latency
Concurrency Must design for scalability and load balancing
Continuous Evolution Must use agile process models and CI/CD pipelines

Aesthetics Must emphasize UX/UI design and responsive layouts

1.5 Software Engineering

Definition

Software Engineering is the application of a systematic, disciplined, quantifiable approach to the development, operation, and maintenance of software; that is, the application of engineering to software. (IEEE Definition)

According to Fritz Bauer: "Software Engineering is the establishment and use of sound engineering principles in order to obtain economically software that is reliable and works efficiently on real machines."

Why Software Engineering?

  • Software Crisis: In the late 1960s-1970s, software projects were consistently being delivered late, over budget, and with defects. The "software crisis" led to the recognition that engineering discipline was needed for software development.
  • Growing Complexity: Modern software systems are incredibly complex, involving millions of lines of code, distributed architectures, and integration with numerous external systems.
  • Quality Requirements: Users demand high-quality, reliable, and secure software. Ad-hoc development approaches cannot consistently deliver this quality.
  • Cost Control: Software development is expensive. Engineering practices help manage costs through better planning, estimation, and process management.
  • Maintenance: 60-80% of all software costs are maintenance costs. Well-engineered software is easier and less expensive to maintain.

Software Engineering Layers

Software engineering is a layered technology with four fundamental layers:

  1. Quality Focus (Foundation): The bedrock that supports software engineering. Any engineering approach must rest on an organizational commitment to quality. Total quality management (TQM), Six Sigma, and similar philosophies foster a continuous process improvement culture.
  2. Process: The foundation for software engineering. Process defines a framework that establishes the context in which the methods are applied, the work products are produced, milestones are established, quality is ensured, and change is properly managed.
  3. Methods: Provide the technical "how-to's" for building software. Methods encompass a broad array of tasks: communication, requirements analysis, design modeling, program construction, testing, and support.
  4. Tools: Provide automated or semi-automated support for the process and methods. When tools are integrated so that information created by one tool can be used by another, a system called Computer-Aided Software Engineering (CASE) is established.

1.6 The Software Process

Definition

A software process is a framework for the activities, actions, and tasks that are required to build high-quality software. A process defines the approach that is taken as software is engineered. It also encompasses a set of umbrella activities that are applicable across the entire software process.

Generic Process Framework

A process framework establishes the foundation for a complete software engineering process. It identifies a small number of framework activities that are applicable to all software projects, regardless of size or complexity:

  1. Communication: Involves heavy communication and collaboration with the customer (and other stakeholders). The intent is to understand the stakeholders' objectives for the project and to gather requirements that help define software features and functions.
  2. Planning: Creates a "map" that guides the team as it makes the journey. The map defines the software engineering work by describing the technical tasks to be conducted, the risks that are likely, the resources that will be required, the work products to be produced, and a work schedule.
  3. Modeling: Creates models (analysis and design) to better understand software requirements and the design that will achieve those requirements. Models include data models, functional models, and behavioral models.
  4. Construction: Combines code generation (either manual or automated) and the testing that is required to uncover errors in the code. This includes both coding and unit testing activities.
  5. Deployment: The software is delivered to the customer who evaluates the delivered product and provides feedback based on the evaluation. Includes installation, training, and support activities.

Umbrella Activities

In addition to framework activities, software engineering also includes umbrella activities that are applied throughout the process:

  • Software project tracking and control — assessing progress against the project plan
  • Risk management — assessing risks that may affect the project outcome
  • Software quality assurance — defining and conducting activities to ensure quality
  • Technical reviews — assessing work products to uncover and remove errors before propagation
  • Measurement — defining and collecting process, project, and product measures
  • Software configuration management — managing the effects of change
  • Reusability management — defining criteria for work product reuse and establishing mechanisms
  • Work product preparation and production — creating models, documents, logs, forms, and lists

1.7 Software Engineering Practice

The Essence of Practice

George Pólya, in his book How to Solve It, outlined the essence of problem solving (and hence the essence of software engineering practice):

  1. Understand the Problem (Communication and Analysis)
    • Who has a stake in the solution? (stakeholders)
    • What are the unknowns? (data, functions, features, behavior)
    • Can the problem be compartmentalized? (sub-problems)
    • Can the problem be represented graphically? (analysis model)
  2. Plan a Solution (Modeling and Software Design)
    • Have you seen similar problems before?
    • Has a similar problem been solved? (reusable patterns)
    • Can sub-problems be defined? (design decomposition)
    • Can you represent a solution in a way that leads to effective implementation? (design model)
  3. Carry Out the Plan (Construction / Code Generation)
    • Does the solution conform to the plan? (design maps to code)
    • Is each component part of the solution provably correct? (code reviews, unit tests)
  4. Examine the Result (Testing and Quality Assurance)
    • Is it possible to test each component part of the solution?
    • Does the solution produce results that conform to the data, functions, and features required?

General Principles of Practice

David Hooker has proposed seven principles that focus on software engineering practice as a whole. These complement the "how-to" steps described above.

1.8 General Principles

David Hooker's Seven Principles of software engineering provide guidelines for both practitioners and managers:

  1. The Reason It All Exists: A software system exists for one reason — to provide value to its users. All decisions should be made with this in mind. Before specifying a system requirement, before noting a piece of system functionality, before determining the hardware platforms or development processes, ask yourself: "Does this add real value to the system?" If the answer is no, don't do it.
  2. KISS (Keep It Simple, Stupid!): All design should be as simple as possible, but no simpler. This facilitates having a more easily understood and easily maintained system. This is not to say that features, even internal features, should be discarded in the name of simplicity. Rather, the design should not be more complicated than it needs to be.
  3. Maintain the Vision: A clear vision is essential to the success of a software project. Without one, a project almost always ends up being "two-faced." Without conceptual integrity, a system threatens to become a patchwork of incompatible designs held together by the wrong kind of screws.
  4. What You Produce, Others Will Consume: Always specify, design, and implement knowing that someone else will have to understand what you are doing. The audience for any product of software development is potentially large. Specify with an eye to the users. Design keeping the implementers in mind. Code with concern for those who must maintain and extend the system.
  5. Be Open to the Future: A system with a long lifetime has more value. In today's computing environments, software lifetimes are measured in months or years, not decades. However, true "industrial-strength" software systems must endure far longer. Never design yourself into a corner. Always ask "what if" and prepare for all possible answers by creating systems that solve the general problem, not just the specific one.
  6. Plan Ahead for Reuse: Reuse saves time and effort. Achieving a high level of reuse is arguably the hardest goal to accomplish in developing a software system. The reuse of code and designs has been proclaimed as a major benefit of using OO technologies, and yet the return on this investment is not always realized.
  7. Think! This last principle is probably the most overlooked. Placing clear, complete thought before action almost always produces better results. When you think about something, you are more likely to do it right. You also gain knowledge about how to do it right again.

1.9 Software Myths

Software myths — erroneous beliefs about software and the process used to build it — can be traced to the earliest days of computing. Myths have a number of attributes that make them insidious: they appear to be reasonable statements of fact, they have an intuitive feel, and they are often promulgated by experienced practitioners.

Management Myths

  • Myth: "We already have a book that's full of standards and procedures for building software. Won't that provide my people with everything they need to know?"
    Reality: The book of standards may very well exist, but is it used? Are software practitioners aware of its existence? Does it reflect modern software engineering practice? Is it complete? Is it adaptable? In many cases, the answer to all of these questions is "no."
  • Myth: "If we get behind schedule, we can add more programmers and catch up."
    Reality: This is known as Brooks's Law — "Adding manpower to a late software project makes it later." When new people are added, the existing staff must spend time educating newcomers, thereby reducing productive development effort. Communication overhead increases dramatically with more people (n(n-1)/2 communication paths).
  • Myth: "If I decide to outsource the software project to a third party, I can just relax and let that firm build it."
    Reality: If an organization does not understand how to manage and control software projects internally, it will invariably struggle when it outsources. Outsourcing requires clear specifications, active management, and contractual oversight.

Customer Myths

  • Myth: "A general statement of objectives is sufficient to begin writing programs — we can fill in the details later."
    Reality: A poor upfront definition is the major cause of failed software efforts. A formal and detailed description of the information domain, function, behavior, performance, interfaces, design constraints, and validation criteria is essential. These characteristics can be determined only through thorough customer-developer communication.
  • Myth: "Software requirements continually change, but change can be easily accommodated because software is flexible."
    Reality: It is true that software requirements change, but the impact of change varies with the time at which it is introduced. If changes are requested early (before design or code), the cost impact is relatively small. However, as time passes, the cost impact grows rapidly — a change late in the project can be 60 to 100 times more expensive than the same change made early.

Practitioner's Myths

  • Myth: "Once we write the program and get it to work, our job is done."
    Reality: Industry data indicates that between 60% and 80% of all effort expended on software will be expended after it is delivered to the customer for the first time. Maintenance is the most costly phase.
  • Myth: "Until I get the program 'running,' I have no way of assessing its quality."
    Reality: One of the most effective software quality assurance mechanisms can be applied from the inception of a project — the formal technical review. Software reviews are quality filters that have been found to be more effective than testing for finding certain classes of software defects.
  • Myth: "The only deliverable work product for a successful project is the working program."
    Reality: A working program is only one part of a software configuration that includes many elements: documentation (requirements, design, test plans), models, source code, test cases, and user manuals. These work products provide the foundation for successful engineering and ongoing maintenance.
  • Myth: "Software engineering will make us create voluminous and unnecessary documentation and will invariably slow us down."
    Reality: Software engineering is not about creating documents. It is about creating quality through disciplined process. Better analysis means less rework. Better design means fewer bugs. The result is faster delivery, not slower. Documentation, when done properly, improves communication and reduces errors.
Summary: Recognizing and challenging software myths is the first step toward adopting proper software engineering practices. Many project failures can be traced directly to the acceptance of these myths by management, customers, or practitioners.
