Unit 4: Design Concepts [6 Hrs.]

5.1 The Evolution of Software Design

What is Software Design?

Software design is the process of defining the architecture, components, interfaces, and other characteristics of a system or component. It translates the requirements model (what) into a design model (how). Design sits at the kernel of software engineering and is applied regardless of the development process model that is used.

Evolution of Software Design

The history of software design traces the evolution from ad-hoc coding to sophisticated engineering disciplines:

Era Approach Key Concepts
1950s-1960s Code and Fix No formal design; write code, debug, patch
Late 1960s Structured Programming Top-down design, stepwise refinement (Dijkstra, Wirth)
1970s Structured Design Modules, coupling, cohesion (Yourdon, Constantine)
1980s Data-Oriented Design Jackson Structured Programming, Warnier-Orr
Late 1980s-1990s Object-Oriented Design Classes, inheritance, polymorphism, encapsulation
1990s-2000s Pattern-Based Design Design patterns (GoF), architectural patterns
2000s-Present Agile/Component-Based Microservices, API design, domain-driven design

Design Concepts

A set of fundamental design concepts has evolved over the history of software engineering. Each provides the software designer with a foundation from which more sophisticated design methods can be applied:

1. Abstraction

Abstraction allows designers to focus on solving a problem at a certain level of generalization without regard to irrelevant low-level details. There are different levels of abstraction:

  • Procedural Abstraction: A named sequence of instructions that has a specific and limited function (e.g., a function "openDoor" abstracts the detailed steps of opening a door)
  • Data Abstraction: A named collection of data that describes a data object (e.g., "Door" with attributes: type, swing direction, opening mechanism, weight)
  • Control Abstraction: A program control mechanism without specifying internal details (e.g., a semaphore in an operating system)

2. Architecture

Software architecture alludes to the overall structure of the software and the ways in which that structure provides conceptual integrity for a system. Architecture defines the components, their interactions, and the constraints that govern them.

Common Architectural Styles:

  • Layered Architecture: Organizes the system into layers (e.g., Presentation, Business Logic, Data Access)
  • Client-Server: Separates clients that request services from servers that provide them
  • Pipe and Filter: Data flows through a series of processing components (filters) connected by pipes
  • Model-View-Controller (MVC): Separates data model, user interface, and control logic
  • Microservices: Decomposes application into small, independently deployable services
  • Event-Driven: Components communicate through events
  • Repository/Blackboard: Components share data through a central repository
  Layered Architecture Example:

  ┌─────────────────────────────────┐
  │     Presentation Layer          │  (UI / Views / Controllers)
  ├─────────────────────────────────┤
  │     Business Logic Layer        │  (Services / Use Cases)
  ├─────────────────────────────────┤
  │     Data Access Layer           │  (Repositories / DAOs)
  ├─────────────────────────────────┤
  │     Database Layer              │  (PostgreSQL / MongoDB)
  └─────────────────────────────────┘

3. Modularity

Modularity is the attribute of software that allows a program to be intellectually manageable. Software is divided into separately named and addressable components, called modules, that are integrated to satisfy problem requirements.

  • Divides the system into manageable pieces
  • Each module performs a specific function
  • Modules can be developed, tested, and maintained independently
  • Reduces complexity by managing smaller units
Meyer's Criteria for Modularity:
  • Modular decomposability — can be decomposed into sub-problems
  • Modular composability — can be combined to produce new systems
  • Modular understandability — can be understood as a standalone unit
  • Modular continuity — small changes result in changes to few modules
  • Modular protection — errors are confined within a module

4. Information Hiding

Information hiding (proposed by David Parnas) suggests that modules should be characterized by design decisions that each hides from all others. Modules should be specified and designed so that information (procedure and data) contained within a module is inaccessible to other modules that have no need for such information.

  • Reduces coupling between modules
  • Protects modules from the effects of changes in other modules
  • Leads to better encapsulation

5. Functional Independence

The concept of functional independence is achieved by developing modules with "single-minded" function and an "aversion" to excessive interaction with other modules. Independence is measured using two qualitative criteria:

Cohesion

Cohesion is a measure of how closely the elements within a module are related to each other. High cohesion is desirable.

Type Description Quality
Functional Cohesion Every element contributes to a single well-defined function Best (Highest)
Sequential Cohesion Output of one element is input to the next Good
Communicational Cohesion Elements operate on the same data Acceptable
Procedural Cohesion Elements are related by order of execution Moderate
Temporal Cohesion Elements are grouped by when they are executed (e.g., initialization) Poor
Logical Cohesion Elements perform similar but different functions selected by a flag Bad
Coincidental Cohesion Elements have no meaningful relationship Worst (Lowest)

Coupling

Coupling is a measure of the degree of interdependence between modules. Low coupling is desirable.

Type Description Quality
Data Coupling Modules communicate through simple data parameters Best (Lowest)
Stamp Coupling Modules share a composite data structure but use only parts Good
Control Coupling One module passes a control flag to another Moderate
External Coupling Modules share externally imposed data format or protocol Acceptable
Common Coupling Modules share global data Bad
Content Coupling One module modifies internal data of another Worst (Highest)

6. Refinement

Stepwise refinement is a top-down design strategy originally proposed by Niklaus Wirth. A program is developed by successively refining levels of procedural detail. At each step, one or more instructions of the program are decomposed into more detailed instructions.

7. Refactoring

Refactoring is a reorganization technique that simplifies the design (or code) of a component without changing its function or behavior. It improves the internal structure while preserving external behavior.

  • Remove redundant code
  • Simplify complex expressions
  • Extract methods for better readability
  • Rename variables/methods for clarity
  • Replace conditionals with polymorphism

5.2 Software Design Strategies, Interface Analysis and Design

Design Strategies

There are several fundamental strategies for designing software:

Top-Down Design

  • Start with the highest level of abstraction
  • Decompose the system into sub-systems and modules
  • Continue decomposition until each module is simple enough to implement
  • Useful for understanding the overall system structure

Bottom-Up Design

  • Start with the most basic components
  • Combine them into higher-level components
  • Continue until the entire system is assembled
  • Useful when building on existing reusable components

Interface Analysis

Interface analysis examines the interactions between the system and its environment (users, other systems, devices). Key aspects include:

  • User Interfaces (UI): How humans interact with the system
  • External Interfaces: How the system connects to other systems
  • Internal Interfaces: How modules within the system communicate

Interface Design Steps

  1. Analyze users: Understand who will use the interface, their expertise level, and their tasks
  2. Define interface objects and actions: Identify the objects users manipulate and actions they perform
  3. Create interface layout: Design screen layouts, menus, forms, and dialogs
  4. Define navigation flow: How users move between screens/pages
  5. Evaluate and refine: Test with real users and iterate on the design

Golden Rules of Interface Design (Shneiderman)

  1. Strive for consistency: Consistent sequences of actions, identical terminology in prompts, menus, and help screens
  2. Enable frequent users to use shortcuts: Abbreviations, function keys, hidden commands, macro facilities
  3. Offer informative feedback: For every user action, there should be a system response
  4. Design dialogs to yield closure: Groups of actions should have a beginning, middle, and end
  5. Offer simple error handling: The system should detect errors and offer simple, constructive instructions for recovery
  6. Permit easy reversal of actions: Users should be able to undo actions
  7. Support internal locus of control: Users should feel they are in charge of the system
  8. Reduce short-term memory load: Minimize what users need to remember from one screen to the next

WebApp Interface Design

Web application interface design has additional considerations:

  • Responsive Design: Interface must work across devices (desktop, tablet, mobile)
  • Accessibility: Follow WCAG guidelines for users with disabilities
  • Cross-Browser Compatibility: Must work consistently across browsers
  • Performance: Fast loading times are critical for user retention
  • Progressive Enhancement: Core functionality works without JavaScript; enhanced experience with it

5.3 Design Patterns

What is a Design Pattern?

A design pattern is a general, reusable solution to a commonly occurring problem within a given context in software design. It is not a finished design that can be transformed directly into code; rather, it is a description or template for how to solve a problem that can be used in many different situations.

Pattern-Based Software Design

Pattern-based design creates new applications by using existing knowledge about patterns that have been encountered in previous applications. The GoF (Gang of Four) catalog defines 23 classic design patterns organized into three categories:

1. Creational Patterns

Deal with object creation mechanisms:

Pattern Purpose When to Use
Singleton Ensures only one instance exists Database connections, logging, configuration
Factory Method Defines an interface for creating objects When class creation logic is complex
Abstract Factory Creates families of related objects Cross-platform UI components
Builder Separates construction from representation Complex objects with many optional parameters
Prototype Creates objects by cloning When object creation is expensive

2. Structural Patterns

Deal with object composition:

Pattern Purpose When to Use
Adapter Converts interface of a class to another Integrating legacy or third-party code
Bridge Separates abstraction from implementation Multiple implementations of an abstraction
Composite Treats individual objects and compositions uniformly Tree structures (file systems, org charts)
Decorator Adds responsibilities dynamically Extending functionality without subclassing
Facade Provides simplified interface to complex subsystem Simplifying complex API usage
Proxy Provides a surrogate for another object Lazy loading, access control, caching

3. Behavioral Patterns

Deal with communication between objects:

Pattern Purpose When to Use
Observer Notifies dependent objects of state changes Event systems, pub-sub, reactive UIs
Strategy Defines a family of interchangeable algorithms Multiple sorting/searching algorithms
Command Encapsulates a request as an object Undo/redo, queuing, logging operations
Iterator Sequential access without exposing internals Traversing collections
State Alters behavior when internal state changes State machines, workflow engines
Template Method Defines skeleton; subclasses fill in steps Framework hooks, algorithm structure

Architectural Patterns

  • MVC (Model-View-Controller): Separates data, presentation, and control logic
  • MVP (Model-View-Presenter): Variation of MVC where presenter mediates between model and view
  • MVVM (Model-View-ViewModel): Uses data binding to synchronize view and model
  • Repository Pattern: Abstracts data access behind a repository interface
  • Service-Oriented Architecture (SOA): System composed of loosely coupled services
  • Microservices: Decomposition into small, independently deployable services

User Interface Design Patterns

  • Navigation patterns: Breadcrumbs, hamburger menu, tab bar, sidebar
  • Input patterns: Autocomplete, date picker, stepper, search with filters
  • Data display patterns: Cards, lists, tables, infinite scroll, pagination
  • Feedback patterns: Toasts, modals, progress indicators, skeleton screens

Web App Design Patterns

  • Single Page Application (SPA): Loads a single HTML page and dynamically updates content
  • Server-Side Rendering (SSR): Server generates HTML for each request
  • Static Site Generation (SSG): Pre-renders pages at build time
  • Progressive Web App (PWA): Web app with native-like capabilities
  • REST API Design: Resource-based URLs, HTTP methods, stateless

5.4 Function-Oriented Design

What is Function-Oriented Design?

Function-oriented design (also called structured design) views a system as a set of interacting functions. The system is decomposed into a set of interacting units where each unit has a clearly defined function.

Key Characteristics

  • Focuses on the processes/functions the system performs
  • Uses top-down decomposition (functional decomposition)
  • Data flows between functions
  • Functions transform input data into output data
  • Represented using DFDs, Structure Charts

Structure Chart

A structure chart shows the hierarchical structure of modules and how they call each other. It depicts:

  • Modules: Represented as rectangles
  • Calling relationships: Shown as arrows
  • Data parameters: Shown as small circles on arrows
  • Control parameters: Shown as filled circles on arrows
  Structure Chart Example (Order Processing):

                    ┌──────────────────┐
                    │  Process Order   │
                    └──────────────────┘
                     /       |       \
                    /        |        \
    ┌──────────────┐  ┌──────────────┐  ┌──────────────┐
    │ Validate     │  │  Calculate   │  │  Generate    │
    │ Order        │  │  Total       │  │  Invoice     │
    └──────────────┘  └──────────────┘  └──────────────┘
         |                   |                 |
    ┌──────────┐     ┌──────────────┐    ┌──────────┐
    │ Check    │     │  Apply       │    │ Format   │
    │ Inventory│     │  Discount    │    │ Output   │
    └──────────┘     └──────────────┘    └──────────┘

Advantages of Function-Oriented Design

  • Straightforward and easy to understand
  • Well-suited for systems where data processing is the main concern
  • Established techniques (DFD, structure charts) provide clear documentation
  • Good for batch processing and data transformation systems

Disadvantages

  • Separates data from the functions that operate on them
  • Difficult to maintain as requirements change
  • Poor support for data abstraction
  • Not suitable for systems where data is the central concern

5.5 Object-Oriented Design (OOD)

What is Object-Oriented Design?

Object-Oriented Design views a system as a collection of interacting objects. Each object combines both data (attributes) and behavior (methods) into a single entity. OOD is based on the principle that software should be modeled around the objects in the problem domain rather than around functions.

Key OOD Principles

1. Encapsulation

Encapsulation bundles data and the methods that operate on that data within a single class, hiding the internal implementation details from outside access. Only the public interface is exposed.

2. Inheritance

Inheritance allows a new class (derived/child) to inherit the properties and methods of an existing class (base/parent). This promotes code reuse and establishes a natural hierarchy.

3. Polymorphism

Polymorphism allows objects of different classes to be treated as objects of a common superclass. The same interface can have different implementations.

4. Abstraction

Abstraction focuses on the essential characteristics of an object relative to the perspective of the viewer, ignoring properties that are not relevant.

SOLID Principles

The SOLID principles are five design principles for making software designs more understandable, flexible, and maintainable:

Principle Description Example
S — Single Responsibility A class should have only one reason to change Separate UserValidator from UserRepository
O — Open/Closed Open for extension, closed for modification Add new payment types without changing existing code
L — Liskov Substitution Subtypes must be substitutable for their base types Square should properly extend Rectangle behavior
I — Interface Segregation Clients shouldn't depend on interfaces they don't use Split large interfaces into smaller, focused ones
D — Dependency Inversion Depend on abstractions, not concretions Use interfaces/abstract classes instead of concrete implementations

Function-Oriented vs. Object-Oriented Design

Aspect Function-Oriented Design Object-Oriented Design
Focus Functions/processes Objects (data + behavior)
Decomposition Functional decomposition Object decomposition
Data Separate from functions Encapsulated within objects
Reusability Limited High (through inheritance and polymorphism)
Maintainability Difficult (data-function dependency) Easier (encapsulation limits change impact)
Notation DFD, Structure Charts UML (Class, Sequence, State diagrams)
Best For Data processing, batch systems Complex, evolving, interactive systems
Summary: Software design concepts provide the foundation for creating well-structured, maintainable, and extensible software systems. Understanding abstraction, architecture, modularity, coupling, cohesion, and design patterns is essential for every software engineer. The choice between function-oriented and object-oriented design depends on the nature of the problem, but modern systems overwhelmingly favor OOD due to its superior support for complexity management and change accommodation.
