Unit 7: Configuration Management and Software Maintenance [3 Hrs.]

7.1 Software Configuration and Change Management

What is Software Configuration Management (SCM)?

Software Configuration Management (SCM) is a set of activities designed to manage change throughout the software lifecycle. It identifies, organizes, and controls modifications to the software being built — essentially, SCM is the art of coordinating software development to minimize confusion.

Why SCM is Needed

Change is inevitable in software development. Requirements change, designs evolve, bugs are fixed, and new features are added. Without SCM, changes can lead to:

  • Lost modifications or overwritten changes
  • Inability to determine what changed, when, and why
  • Conflicting changes by multiple developers
  • Difficulty in reproducing bugs or reverting to a stable version
  • Inability to track which version a customer is using

Software Configuration Items (SCIs)

A Software Configuration Item (SCI) is anything that is produced during the software engineering process and placed under configuration control:

  • Source code files
  • Documentation (SRS, design docs, test plans, user manuals)
  • Data files and databases
  • Build scripts and makefiles
  • Test cases and test data
  • Libraries and third-party components
  • Configuration files
  • Tools and compilers (versions)

Baselines

A baseline is a specification or product that has been formally reviewed and agreed upon, that thereafter serves as the basis for further development, and that can be changed only through formal change control procedures.

Baseline When Established What It Contains
Functional Baseline After requirements review Approved SRS document
Allocated Baseline After design review Approved design specification
Product Baseline After testing and acceptance Approved code, documentation, test results

Change Management Process

The change management process ensures that changes are introduced in a controlled and coordinated manner:

  1. Change Request: A stakeholder submits a formal request for change (using a Change Request Form)
  2. Change Evaluation: The change is evaluated for:
    • Technical merit and feasibility
    • Impact on existing functionality
    • Cost and effort required
    • Schedule impact
    • Risk assessment
  3. Change Control Board (CCB) Review: A group of stakeholders reviews the change request and the evaluation, then approves, modifies, or rejects the change
  4. Implementation: If approved, the change is implemented following established procedures
  5. Verification: The change is tested and verified
  6. Release: The modified software is released to users
  Change Management Process Flow:

  Change Request → Evaluation → CCB Review → Decision
                                               ↓
                                     ┌────────────────┐
                                     │   Approved?     │
                                     └────────────────┘
                                    Yes/              \No
                                     ↓                  ↓
                              Implementation        Archive
                                     ↓               (Rejected)
                               Verification
                                     ↓
                               Release / Deploy

7.3 Version and Release Management

Version Control

Version control (also called source control or revision control) is the management of changes to documents, programs, and other collections of information. It tracks every modification to the code in a special database.

Version Numbering

The most common version numbering scheme is Semantic Versioning (SemVer): 

  MAJOR.MINOR.PATCH

  MAJOR: Incremented when incompatible API changes are made
  MINOR: Incremented when new functionality is added (backward compatible)
  PATCH: Incremented when backward-compatible bug fixes are made

  Examples:
    1.0.0 → Initial release
    1.0.1 → Bug fix
    1.1.0 → New feature added
    2.0.0 → Breaking change / major rewrite

Version Control Systems

System Type Key Features
Git Distributed Most popular; branching, merging, distributed repos; GitHub, GitLab
SVN (Subversion) Centralized Central server; simpler model; still used in some organizations
Mercurial Distributed Similar to Git; simpler command set
Perforce Centralized Handles large binary files well; used in game development

Git Branching Strategies

  • GitFlow: Uses feature, develop, release, hotfix, and main branches
  • GitHub Flow: Simple model — main branch + feature branches
  • Trunk-Based Development: All developers commit to a single trunk (main) branch
  GitFlow Branching Model:

  main     ──●──────────────────●──────────── (stable releases)
              ↑                  ↑
  release   ──┼──●───●──────────┼──
              ↑  ↑   ↑          ↑
  develop  ──●──●───●──●──●───●──●── (integration branch)
              ↑  ↑       ↑  ↑
  feature  ──●──●       ●──●        (feature branches)

Release Management

Release management is the process of planning, scheduling, and controlling the build, test, and deployment of releases. Key activities include:

  • Creating release plans and schedules
  • Managing release branches in version control
  • Building and packaging release artifacts
  • Managing deployment to various environments (staging, production)
  • Release notes and documentation
  • Rollback procedures

Release Types

Type Description Example
Alpha Release Early, internal testing release v1.0.0-alpha.1
Beta Release External testing with selected users v1.0.0-beta.1
Release Candidate (RC) Feature-complete, final testing v1.0.0-rc.1
General Availability (GA) Production release for all users v1.0.0
Hotfix Emergency fix for critical production issue v1.0.1

7.5 Types of Software Maintenance

What is Software Maintenance?

Software maintenance is defined as the modification of a software product after delivery to correct faults, to improve performance or other attributes, or to adapt the product to a modified environment. It is the most costly phase of the software lifecycle, accounting for 60-80% of total software costs.

Four Types of Maintenance

Type Description % of Effort Example
Corrective Fixing bugs and defects discovered after delivery ~20% Fixing a login error that occurs with special characters
Adaptive Modifying software to accommodate changes in the environment (OS, hardware, regulations) ~25% Updating software to work with a new operating system version
Perfective Enhancing functionality and improving performance based on user feedback ~50% Adding a new search feature requested by users
Preventive Making changes to prevent future problems (re-engineering, refactoring) ~5% Refactoring code to improve maintainability
Key Insight: Perfective maintenance (adding new features and improvements) accounts for the largest share of maintenance effort (~50%). This underscores the importance of designing software that is easy to extend and modify.

7.4 Need for Software Maintenance

Why is Maintenance Necessary?

  • Bug Fixes: No software is perfect at release. Users discover bugs that were not caught during testing.
  • Environment Changes: Operating systems, hardware, networks, and regulations change over time. Software must adapt to remain functional.
  • Business Changes: Business requirements evolve. New features must be added and existing features modified to meet changing needs.
  • Performance Improvements: Users demand faster performance, better usability, and enhanced capabilities over time.
  • Security Updates: New vulnerabilities are discovered regularly. Software must be patched to remain secure.
  • Technology Evolution: New technologies emerge that offer better solutions. Software must be updated to leverage them.

Lehman's Laws of Software Evolution

  1. Continuing Change: A software system must be continually adapted or it becomes progressively less satisfactory in use.
  2. Increasing Complexity: As a program evolves, its complexity increases unless work is done to reduce it.
  3. Self-Regulation: Program evolution is a self-regulating process.
  4. Conservation of Organizational Stability: The rate of effective work on an evolving system is statistically invariant.
  5. Conservation of Familiarity: The incremental change in each release is approximately constant.
  6. Continuing Growth: Functional capability must be continually increased to maintain user satisfaction.
  7. Declining Quality: Quality of evolving systems will decline unless rigorously maintained and adapted.
  8. Feedback System: Evolution processes are multi-level, multi-loop, multi-agent feedback systems.

7.6 Software Maintenance Process Models

Quick-Fix Model

  • Simplest approach: identify the problem, fix it, release
  • No formal analysis of impact or side effects
  • Often leads to degraded software quality over time
  • Acceptable only for trivial changes

Iterative Enhancement Model (Basili)

  1. Analyze existing system and identify areas for improvement
  2. Design modifications
  3. Implement and test changes
  4. Deliver enhanced system
  5. Repeat cycle

Reuse-Oriented Model

  • Focuses on identifying reusable components in the existing system
  • Modifies and extends reusable components for new requirements
  • Reduces maintenance effort through systematic reuse

Boehm's Maintenance Model

Boehm's model considers maintenance as a closed-loop feedback system:

  1. Management decision to modify the system
  2. Understanding of the existing system
  3. Design of the modification
  4. Implementation of the modification
  5. Testing the modified system
  6. Documentation update
  7. Release and delivery

7.7 Software Maintenance Cost

Cost Distribution

Software maintenance typically accounts for 60-80% of the total lifecycle cost of a software system. This makes it the most expensive phase of the SDLC.

Factors Affecting Maintenance Cost

Factor Impact on Cost
Staff stability High turnover increases cost (knowledge loss)
Programming language Low-level languages are harder to maintain
Age of software Older software is more expensive to maintain
Documentation quality Poor documentation significantly increases maintenance effort
Design quality Poorly designed systems are difficult and expensive to modify
External dependencies More dependencies = more maintenance triggers
Domain complexity Complex domains require more effort for maintenance
Configuration management Poor SCM makes tracking and managing changes difficult

Reducing Maintenance Costs

  • Good initial design: Well-designed software is easier and cheaper to maintain
  • Comprehensive documentation: Reduces time to understand the system
  • Coding standards: Consistent code is easier to read and modify
  • Automated testing: Regression tests catch side effects of changes
  • Configuration management: Proper SCM ensures controlled changes
  • Modular architecture: Changes are isolated to specific modules
  • Knowledge management: Document design decisions, rationale, and domain knowledge
  • Continuous refactoring: Prevent accumulation of technical debt
Summary: Software Configuration Management ensures controlled evolution of software through baselines, version control, and formal change management. Software maintenance is the longest and most expensive phase of the SDLC, with perfective maintenance (enhancements) accounting for the largest share. Organizations can reduce maintenance costs through good initial design, comprehensive documentation, and robust SCM practices.

Modern SCM: CI/CD Pipelines and Automation

Continuous Integration in Configuration Management

Modern SCM practices extend beyond traditional version control to encompass Continuous Integration and Continuous Delivery (CI/CD) pipelines that automate the build, test, and deployment processes:

CI/CD Pipeline Stages

  1. Source Stage: Developer commits code to version control (Git). The CI/CD pipeline is automatically triggered by the commit event.
  2. Build Stage: The application is compiled and built. Dependencies are resolved. Build artifacts (executables, packages) are created.
  3. Test Stage: Automated tests are executed — unit tests, integration tests, code quality checks (linting, static analysis), and security scans.
  4. Deploy Stage: If all tests pass, the application is automatically deployed to a staging environment. After approval, it can be deployed to production.
  CI/CD Pipeline in SCM Context:

  Developer          Version Control       CI Server          Environments
  ────────          ───────────────       ─────────          ────────────
  Write Code  ─────→  Git Push     ─────→  Build    ─────→  Staging
  Code Review ←─────  Pull Request ←─────  Test     ─────→  Production
  Fix Issues  ─────→  Merge        ─────→  Deploy   ─────→  Monitoring

Technical Debt and SCM

Technical debt is a metaphor reflecting the implied cost of additional rework caused by choosing easy (limited) solutions now instead of using a better approach that would take longer. SCM practices help manage and reduce technical debt:

Types of Technical Debt

Type Description SCM Strategy
Code Debt Poor code quality, code smells, duplication Code reviews, automated quality gates
Design Debt Suboptimal architecture and design decisions Architecture reviews, design documentation
Testing Debt Insufficient test coverage Coverage thresholds in CI/CD pipeline
Documentation Debt Missing or outdated documentation Documentation requirements in Definition of Done
Infrastructure Debt Outdated dependencies, unsupported platforms Automated dependency scanning and updates

SCM Best Practices Summary

  • Commit frequently: Small, focused commits are easier to review, test, and revert
  • Write meaningful commit messages: Describe what changed and why
  • Use branching strategies: Feature branches, release branches, hotfix branches
  • Automate everything: Build, test, deploy, and quality checks should be automated
  • Tag releases: Use semantic versioning tags for all releases
  • Never commit secrets: Use environment variables or secret management tools
  • Code review all changes: Pull/merge requests with peer review before merging
  • Maintain a clean history: Use squash merges or interactive rebase when appropriate
  • Back up your repository: Ensure repository data is regularly backed up
  • Use .gitignore: Exclude build artifacts, IDE files, and dependencies from version control
