Unit 5: Software Measurement and Metrics [2 Hrs.]

6.1 Software Measurement

What is Software Measurement?

Software measurement is the process of quantifying software attributes to understand, control, predict, and improve software development and maintenance. Measurement provides objective data to support decision-making throughout the software lifecycle.

Lord Kelvin stated: "When you can measure what you are speaking about, and express it in numbers, you know something about it; but when you cannot measure it, your knowledge is of a meager and unsatisfactory kind." This principle applies directly to software engineering.

Why Measure Software?

  • Characterize: Gain understanding of processes, products, resources, and environments. Establish baselines for future comparisons.
  • Evaluate: Determine the status of the project and product with respect to plans. Assess whether quality, schedule, and budget targets are being met.
  • Predict: Develop models to estimate future effort, cost, schedule, and quality. Plan resources and make informed decisions about project direction.
  • Improve: Identify bottlenecks, inefficiencies, and opportunities for improvement. Quantify the impact of process changes and new techniques.

Categories of Software Measures

Category What is Measured Examples
Process Measures The software process itself Time and effort per phase, defect detection rate, review coverage
Product Measures The software product (deliverables) Size (LOC, FP), complexity, quality, reliability
Project Measures Project characteristics Cost, schedule, staffing levels, productivity

Measurement Principles

  1. Formulation: Derive the measures and metrics appropriate for the representation of the software
  2. Collection: Accumulate data needed for the formulated metrics
  3. Analysis: Compute the metrics and apply mathematical tools
  4. Interpretation: Evaluate the metrics results to gain insight
  5. Feedback: Use insights to make recommendations for improvement

Measure vs. Metric vs. Indicator

  • Measure: A quantitative indication of extent, amount, dimension, capacity, or size of some attribute. Example: Number of errors found during testing = 42
  • Metric: A quantitative measure of the degree to which a system, component, or process possesses a given attribute. A metric is derived from one or more measures. Example: Error density = errors / KLOC = 42 / 10 = 4.2 errors per KLOC
  • Indicator: A metric or combination of metrics that provides insight into the software process, product, or project. Example: If error density exceeds 5 errors/KLOC, the module needs additional review.

6.2 Software Metrics, Review Metrics and Their Use

Size-Oriented Metrics

Size-oriented metrics use Lines of Code (LOC) as the primary measure:

Metric Formula Interpretation
Productivity KLOC / person-months Higher = more productive
Quality Defects / KLOC Lower = higher quality
Cost $ / LOC Lower = more cost-effective
Documentation Documentation pages / KLOC Indicates documentation thoroughness

Advantages of LOC

  • Simple and easy to count (automated tools available)
  • Widely used and understood
  • Useful for comparing similar projects in the same language

Disadvantages of LOC

  • Language-dependent (can't compare Java LOC with Python LOC)
  • Penalizes well-designed, concise programs
  • Difficult to estimate early in the project
  • No direct correlation with functionality delivered

Function-Oriented Metrics (Function Points)

Function Point Analysis (FPA), developed by Allan Albrecht at IBM in 1979, measures software size based on the functionality delivered to the user, independent of the programming language used.

Five Information Domain Characteristics

Characteristic Description Example
External Inputs (EI) Data entering the system from outside User login form, data entry screen
External Outputs (EO) Data leaving the system to the user Reports, error messages, screens
External Inquiries (EQ) Input that results in immediate output Search query, lookup
Internal Logical Files (ILF) Data stores maintained by the system Database tables, config files
External Interface Files (EIF) Data stores referenced but not maintained Third-party data files, external APIs

Complexity Weights

Measurement Parameter Simple Average Complex
External Inputs (EI) 3 4 6
External Outputs (EO) 4 5 7
External Inquiries (EQ) 3 4 6
Internal Logical Files (ILF) 7 10 15
External Interface Files (EIF) 5 7 10

Function Point Calculation

  Step 1: Calculate Unadjusted Function Points (UFP)
    UFP = Σ (count × weight) for all five categories

  Step 2: Calculate Value Adjustment Factor (VAF)
    VAF = 0.65 + 0.01 × Σ(Fi)
    where Fi (i = 1 to 14) are General System Characteristics
    rated from 0 (no influence) to 5 (strong influence)

  Step 3: Calculate Adjusted Function Points (AFP)
    AFP = UFP × VAF

  Example:
    EI: 3 Simple × 3 = 9,  2 Average × 4 = 8    → 17
    EO: 2 Simple × 4 = 8,  1 Complex × 7 = 7    → 15
    EQ: 1 Average × 4 = 4                         →  4
    ILF: 2 Simple × 7 = 14, 1 Average × 10 = 10  → 24
    EIF: 1 Simple × 5 = 5                         →  5
    ─────────────────────────────────────────────
    UFP = 17 + 15 + 4 + 24 + 5 = 65

    If Σ(Fi) = 42, then VAF = 0.65 + 0.01 × 42 = 1.07
    AFP = 65 × 1.07 = 69.55 Function Points

Review Metrics

Formal Technical Reviews (FTRs) are a quality assurance mechanism. Metrics from reviews help evaluate their effectiveness:

Review Metric Formula Purpose
Preparation Rate Pages reviewed / preparation hours Ensures reviewers spend adequate time
Review Rate LOC (or pages) / review hours Optimal: 150-200 LOC/hour for code reviews
Defect Density Defects found / size (KLOC or pages) Quality indicator
Defect Detection Rate Defects found in review / total defects Review effectiveness (typically 60-90%)
Review Effort Ratio Review effort / total development effort Typically 10-15% of total effort

Formal Technical Reviews (FTR)

An FTR is a software quality assurance activity performed by software engineers:

  1. Meeting preparation: Each reviewer reviews the work product individually
  2. Review meeting: Reviewers present findings; errors are identified and recorded
  3. Rework: The author fixes identified issues
  4. Follow-up: Verification that all issues have been addressed

FTR Guidelines

  • Review the product, not the producer
  • Set an agenda and maintain it
  • Limit debate and rebuttal
  • Enunciate problem areas but don't attempt to solve every problem
  • Take written notes
  • Limit the number of participants (3-5 reviewers optimal)
  • Develop a checklist for each product to be reviewed
  • Allocate resources and time schedule for FTRs
  • Conduct meaningful training for all reviewers
  • Review earlier reviews

6.3 Control Flow Graph (CFG)

What is a Control Flow Graph?

A Control Flow Graph (CFG) is a graphical representation of the flow of control through a program. Each node represents a basic block (a sequence of statements with no branches), and each edge represents a transfer of control between blocks.

CFG Elements

  • Nodes: Represent one or more procedural statements
  • Edges: Represent flow of control between nodes
  • Predicate Node: A node with two or more edges emanating from it (decision point)
  • Region: An area bounded by edges and nodes (including the area outside the graph)

Example: CFG Construction

  Source Code:                   Control Flow Graph:

  1. void example(int x) {
  2.   int result = 0;           ┌───┐
  3.   if (x > 0) {              │ 1 │ (Statements 1-2)
  4.     result = x * 2;         └─┬─┘
  5.     if (x > 10) {               │
  6.       result += 5;          ┌───┴───┐
  7.     }                       │   2   │ (Predicate: x > 0)
  8.   } else {                  └───┬───┘
  9.     result = -x;           Y/     \N
  10.  }                     ┌───┐     ┌───┐
  11.  printf("%d", result); │ 3 │     │ 6 │ (result = -x)
  12. }                      └─┬─┘     └─┬─┘
                               │         │
                           ┌───┴───┐     │
                           │   4   │     │ (Predicate: x > 10)
                           └───┬───┘     │
                          Y/     \N      │
                       ┌───┐  ┌───┐      │
                       │ 5 │  │   │      │
                       └─┬─┘  └─┬─┘      │
                         │      │        │
                         └──┬───┘        │
                            └─────┬──────┘
                              ┌───┴───┐
                              │   7   │ (printf)
                              └───────┘

6.4 Cyclomatic Complexity

What is Cyclomatic Complexity?

Cyclomatic complexity, defined by Thomas McCabe, is a software metric that provides a quantitative measure of the logical complexity of a program. It measures the number of linearly independent paths through a program's source code.

Calculation Methods

There are three ways to compute cyclomatic complexity V(G):

Method 1: Edges and Nodes

  V(G) = E - N + 2

  Where:
    E = number of edges in the control flow graph
    N = number of nodes in the control flow graph

Method 2: Predicate Nodes

  V(G) = P + 1

  Where:
    P = number of predicate nodes (decision points/conditions)

Method 3: Regions

  V(G) = Number of regions in the control flow graph

  (A region is an area bounded by edges and nodes,
   including the exterior unbounded region)

Worked Example

  Consider this code:

  1. void analyze(int a, int b) {
  2.   if (a > 0 && b > 0) {      // Predicate 1 (two conditions = 2 predicates)
  3.     printf("Both positive");
  4.   } else if (a == 0) {         // Predicate 3
  5.     printf("A is zero");
  6.   } else {
  7.     printf("Other case");
  8.   }
  9.   printf("Done");
  10. }

  Predicate nodes: 3 (a > 0, b > 0, a == 0)
  V(G) = 3 + 1 = 4

  This means there are 4 linearly independent paths:
  Path 1: a > 0, b > 0  → "Both positive" → "Done"
  Path 2: a > 0, b ≤ 0, a == 0  → "A is zero" → "Done"
  Path 3: a > 0, b ≤ 0, a ≠ 0  → "Other case" → "Done"
  Path 4: a ≤ 0, a == 0  → "A is zero" → "Done"

Interpreting Cyclomatic Complexity

V(G) Range Risk Evaluation Action
1 - 10 Simple, low risk Well-structured, easy to test
11 - 20 Moderate complexity, moderate risk Consider refactoring
21 - 50 Complex, high risk Refactoring recommended
> 50 Very complex, very high risk Must refactor; untestable

Significance of Cyclomatic Complexity

  • Provides the minimum number of test cases needed for basis path testing
  • Identifies modules that are too complex and need refactoring
  • Provides an objective measure of code quality
  • Can be automated (tools: SonarQube, PMD, Lizard, radon)
  • Useful as a quality gate in CI/CD pipelines

6.5 Object-Oriented Metrics

CK Metrics Suite (Chidamber and Kemerer)

The CK metrics suite is the most widely used set of object-oriented metrics:

Metric Name Description Ideal
WMC Weighted Methods per Class Sum of complexities of all methods in a class Low (≤ 20)
DIT Depth of Inheritance Tree Maximum depth from class to root of hierarchy Low (≤ 5)
NOC Number of Children Number of immediate subclasses Moderate
CBO Coupling Between Object classes Number of other classes to which a class is coupled Low (≤ 14)
RFC Response For a Class Number of methods that can be executed in response to a message Low
LCOM Lack of Cohesion in Methods Degree to which methods in a class are unrelated Low (0 = perfect cohesion)

Additional OO Metrics

  • Lines of Code per Method: Average method size (ideal: 10-20 lines)
  • Number of Methods per Class: Class size indicator (ideal: ≤ 20)
  • Fan-in/Fan-out: Number of modules calling/called by a module
  • Code Coverage: Percentage of code executed during testing

6.6 Lossless Decomposition

What is Lossless Decomposition?

In the context of software measurement and metrics, lossless decomposition refers to the principle that when a large software component is decomposed into smaller components, the total measured attributes should be preserved. No information or functionality should be lost during decomposition.

Application in Software Engineering

  • Functional Decomposition: When a function is broken into sub-functions, the sum of functionality should equal the original function
  • Metric Preservation: When measuring decomposed components, the total function points or LOC should sum to the original measurement
  • Requirements Decomposition: When a high-level requirement is broken into sub-requirements, all aspects of the original requirement should be covered
  • Database Normalization: Lossless-join decomposition ensures no data is lost when a relation is decomposed into sub-relations (related to database design theory)

Significance in Metrics

Lossless decomposition is important because it ensures that metrics remain meaningful and accurate when systems are broken down for analysis. If decomposition introduces loss, measurements at the component level will not accurately reflect the system-level characteristics, leading to flawed conclusions about quality, complexity, and effort.

Summary: Software measurement and metrics provide the quantitative foundation for managing software projects and improving software quality. Key metrics include LOC, function points, cyclomatic complexity, and OO metrics (CK suite). Formal technical reviews are one of the most effective quality assurance mechanisms. Understanding and applying these metrics enables data-driven decision making throughout the software development lifecycle.
